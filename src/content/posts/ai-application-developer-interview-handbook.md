## 一、必备知识点清单

> 原则：简历写了什么，就要能讲什么。每条先用 1 分钟讲清"是什么"，再准备 1 分钟"怎么做的"。

### 1. RAG 全链路（简历 C 位，必被深挖）

- **分块（Chunking）策略**：固定大小 vs 语义分块 vs 父子分块；overlap（重叠）的作用；为什么分块策略直接决定检索质量
  - 面试答法：chunk 太大 → 上下文稀释 + token 成本高；chunk 太小 → 信息不完整

**2026 分块最佳实践（升级版,已调研,面试背这些）**：
- **默认起点**:RecursiveCharacterTextSplitter,chunk_size **400-512 tokens**,overlap **10-20%**(50-100 tokens)——80% RAG 应用的默认选择;分隔符 `["\n\n","\n"," ",""]`
- **固定大小分块已不是主流**:只适合原型;生产系统主流 = 结构化感知 + 语义 + 层级
- **按查询类型调参(NVIDIA 2024)**:事实型查询(名称/日期)→ 256-512 tokens;分析型查询(解释/对比)→ 1024+ tokens;混合型 400-512 起步;内容类型与查询类型冲突时,内容类型优先
- **父子分块(生产 RAG 行业标准)**:Parent 1500 tokens 拆 5×300 Child;**只索引 Child,命中时返回 Parent 给 LLM**——"小块好命中、大块好思考"
- **结构化感知分块(2026 最重要趋势)**:Markdown 产物 → MarkdownHeaderTextSplitter 按标题切 + **标题前置拼接(Contextual Chunking)**:把标题链拼进每个子 chunk,如 `# 2025 Model X 说明书 > ## 电池续航` + 内容,防跨域误检索;Anthropic Contextual Retrieval 同族
- **混合路由**:PDF→页面级(NVIDIA 冠军 accuracy 0.648)、网页→递归、代码→AST 感知
- **Benchmark 背 3 个数**:NVIDIA 页面级 0.648;Chroma 语义分块 recall 0.919 vs 递归 0.885(差 3pp 但语义贵);策略选错 recall 差可达 9%
- **反直觉 2026 发现**:Vecta 基准递归 512-token 69% > 语义分块 54%(碎片化);overlap 在部分评测无可测收益——语义分块不是越高级越好,按文档实测
- **面试答法升级版**:"分块默认递归 400-512 tokens + 10-20% overlap;需要精度时上语义/父子分块;PDF 走页面级;结构化文档用 Markdown 标题切分+标题前置拼接,避免片段脱离上下文"
- **Embedding 与向量检索**：向量模型把文本映射为高维向量，语义相近则向量距离近；ANN（近似最近邻）检索，索引如 HNSW / IVF
- **混合检索为什么好**：向量（语义） + BM25（关键词精确）互补；GraphRAG（实体抽取 → 图结构 → 社区摘要）适合"跨文档关系"类问答
- **RRF（Reciprocal Rank Fusion）**：对多路结果按 `1/(k+rank)` 打分求和（k 常用 60），免权重调参融合多路检索结果
- **重排序（Rerank）**：双塔模型负责召回（快、粗），Cross-Encoder 负责精排（慢、准，query+doc 一起看）；在 Top-N 结果上做二次排序
- **评估指标（RAGAS）**：Faithfulness（忠实度）、Answer Relevancy（答案相关性）、Context Precision（上下文精确率）、Context Recall（上下文召回率）——至少能背出 2 个
- **幻觉（Hallucination）**：模型编造不存在的知识；缓解手段 = RAG 兜底 + 引用来源 + 提示词约束

### 2. Agent 与 LangGraph（项目一核心）

- **Agent 四要素闭环**：感知 → 规划 → 工具调用 → 反思
- **ReAct 模式**：Reasoning + Acting 交替循环，边推理边调用工具，把中间结果喂回模型
- **LangGraph 与 LangChain 区别**：
  - LangChain 的 LCEL 是声明式链：`prompt | model | parser`，线性/单向
  - LangGraph 是状态图：节点（处理函数）+ 边（条件路由）+ 共享 State，支持循环、分支、状态持久化、人工中断
  - 面试答法：需要复杂流程控制（多步工具循环、条件分支、状态保持）选 LangGraph
- **Supervisor-Workers 模式**：Supervisor（管理者）决策任务分给哪个 Worker；Worker 各自负责检索 / SQL / 代码执行 / 数据分析
- **Tool Calling**：模型输出结构化工具名 + 参数 → 系统执行 → 结果回填给模型 → 模型继续
- **LangMem 长期记忆**：长期记忆（向量化写入存储）+ 短期记忆（对话历史）；解决多轮会话上下文丢失
- **A2A 协议**：Agent-to-Agent，负责智能体之间互联（Agent 的 HTTP）；与 MCP 分工不同（MCP 连工具，A2A 连 Agent）
- **Agentic RAG（智能检索）**：不被动等用户检索条件，Agent 自主判断"要不要查、查什么"再检索

### 3. MCP（2026 最热点，最高频考点）

- 一句话定义：**"AI 界的 USB-C"**——统一大模型与外部工具/数据源的对接协议
- 架构：**MCP Client（模型侧）↔ MCP Server（工具侧）**，Server 暴露三类能力：Tools（工具）/ Resources（资源）/ Prompts（提示模板）
- 传输方式：本地 stdio、远程 HTTP/SSE
- 面试答法："在我的项目里通过 MCP 接入外部工具，避免为每个模型写定制集成，一次开发多模型适配"

### 4. 模型与推理（项目二相关）

- **vLLM 优化原理**：PagedAttention（KV Cache 分页管理，减少显存碎片）+ 连续批处理（continuous batching，批内动态进出请求）
- **OpenAI 兼容协议**：统一 `/v1/chat/completions` 接口，各家模型用一套接口接入
- **熔断器（Circuit Breaker）**：三态 CLOSED（正常）→ OPEN（失败次数超阈值，直接拒绝）→ HALF_OPEN（放行少量试探请求验证恢复）
  - 简历参数：5 次失败熔断 / 30 秒后进入半开
- **降级 / 故障转移**：按优先级（priority）排序候选模型，后端不可用自动换下一个

### 5. 流式与实时通信

- **SSE**：单向（服务端 → 客户端），基于 HTTP，自带自动重连，适合"推送结果"
- **WebSocket**：双向全双工，适合"持续对话 / 双向消息"
- 简历中的用法：项目一用 WebSocket 推 Agent 思考过程（交互是双向的），项目二用 SSE 推 token（只是单向下发结果）——面试答法："一个是对话过程双向，另一个只是结果单向推送"

### 6. 数据库速记（每个 1 句话）

- **PostgreSQL vs MySQL**：同为关系型，SQL 相通；PG 类型系统更严格、可扩展性强（pgvector），MySQL 更普及、运维人更多
- **pgvector**：PostgreSQL 向量扩展，SQL 中直接存 embedding 做相似度检索——"我熟悉 PostgreSQL，如需可快速切入"
- **FAISS / ChromaDB / Qdrant**：FAISS 是算法库（非数据库）；ChromaDB 适合本地开发快速验证；Qdrant 是生产级专用向量库（先进过滤/超大规模）
- **Neo4j**：图数据库，放知识图谱关系，GraphRAG 的载体
- **MongoDB**：文档型 NoSQL，"与关系型不同范式，了解层面"

### 7. 工程化 / 部署（简历写了的都要讲清）

- **Docker Compose**：多服务编排；healthcheck（健康检查）探活失败自动重启/标记不健康
- **GitHub Actions + GHCR**：CI 流水线 push 时自动构建镜像推送到 GHCR（容器镜像仓库），部署端拉取
- **Alembic**：数据库 schema 版本迁移工具（自动生成版本脚本：`revision` / `upgrade head`）
- **Nginx 反向代理**：域名接入、端口转发、负载、/静态资源；和 systemd（服务进程托管，开机自启）配合
- **Prometheus**：指标采集（服务暴露 metrics 端点，Prometheus 定时抓取），配合 Grafana 看板
- **pytest + 覆盖率 91.8%**：单元测试 + 集成测试，`coverage` 统计
- **JWT**：header.payload.signature 三段式，无状态认证，服务器只验签不存会话
- **速率限制**：令牌桶 / 滑动窗口算法
- **Token 估算（无 tokenizer）**：不想在服务里引入 tokenizer 库开销，用启发式（中文字符数、英文词数加权估算）——代价是精度低，换来轻量快速

### 7.5 团队协作流程科普（被问"你们怎么协作"必备）

**完整流程（背这个链条）**：
> git clone 拉项目 → 建 feature 分支 → 写代码 → **本地跑单测**（自己验证代码逻辑）→ commit → **push 推到远程分支**（自己就能做）→ **发 MR/PR 提合并请求**（GitLab 叫 MR，GitHub 叫 PR，同一个东西）→ CI 自动检查（静态分析/单测）→ **Code Review 同事评审** → 通过后 **merge 合并到主干** → 部署到测试环境 → **QA 功能测试** → 发布上线（大版本可灰度）

**术语对照**：
- **commit** = 本地提交保存；**push** = 推到远程分支（不需要别人批准）
- **MR / PR** = Merge Request / Pull Request，请求合并，发起后别人才开始看
- **Code Review** = 同事看你的 diff（改动差异），不是用眼看整份代码——重点盯边界条件、安全、风格、设计取舍；在 diff 上留言 → 你修改 → 重新 push → approve 批准 → 合并
- **QA = Quality Assurance（质量保证）**，测试工程师做功能测试——⚠️ 不是 Question and Answer（问答），面试说错就露怯
- **单元测试**（开发自己写，测代码逻辑，push 前跑） vs **功能测试**（QA 做，测功能符合需求，合并部署后跑）——两个概念

**质量三层保障（面试加分句）**：
> "第一层 CI + AI 自动化检查（格式、静态分析、单测）；第二层人工 Code Review——AI 能拦低级错误，但业务上下文和设计权衡必须人来判断，也是团队知识传递；第三层 QA 功能测试。三层过了才合并发布。"

**企业代码仓库**：公司业务代码用私有仓库（GitLab 自建 / Gitee 企业版 / GitHub Enterprise），登录用 SSO + SSH 密钥 / 个人访问令牌（不是"账号密码"）；公开 GitHub 只放开源项目。CI 工具：GitHub Actions / GitLab CI 等。

**发音**：push（普嘘）/ Merge（莫及）/ Review（瑞维优）/ QA 读字母 Q-A / 灰度 huī dù（不是"红组"）

### 8. AI 工具链（加分项但别翻车）

- **Claude Code / Codex / OpenCode**：AI 编程助手，深度使用提效——面试往往反问"你怎么用它提效的"（答：生成测试、批量重构、读代码）
- **OpenClaw / Hermes Agent**：自托管智能体，Docker + systemd 常驻——能讲清部署架构（命令、目录、mcp.json 配置）即可

### 9. 其他（简历点名的零碎）

- **ARQ / Celery**：Python 异步任务队列（broker + worker + 任务定义）
- **Django / Flask**：了解层面。"主用 FastAPI，Django/Flask 的概念（MVC、路由、ORM）相通，上手快"
- **LangSmith / Langfuse**：LLM 应用链路追踪（trace、运行、token 成本）；**RAGAS / deepeval**：RAG 效果评估框架
  - 诚实边界话术："我了解追踪与评估的机制，目前项目在 Prometheus 层做了系统监控，LLM 链路评估计划用 RAGAS 落地"

## 二、模拟面试题库

### A. 开场 · 自我介绍（1 分钟版）

> 各位面试官好，我目前做 AI 应用开发，有 4 年经验。前两年做数据分析，2024 年起专注 LLM 应用开发，独立交付了两个项目——一个是多智能体 RAG 知识库问答系统（500+ 文档，三路混合检索 + Rerank），一个是统一模型网关（多模型接入、熔断降级、SSE 流式）。我能独立完成从需求分析、架构设计到部署上线的完整交付。

要点：控制在 1 分钟；结尾落在"我能做什么"而不是背履历。

### B. 基础必考（每题 1 分钟答完）

1. **RAG 是什么？为什么要用？**
   - 答：外部知识库检索 → 拼进提示词 → 生成答案。解决三个问题：私有数据、知识过时、幻觉。
2. **分块策略怎么选？**
   - 答：先看文档类型——表格/法规类用结构化，长文用语义分块或父子分块；overlap 保证上下文连续；总之需要实验（多 chunk 策略调优）而不是一把梭。
3. **检索怎么找最相关的？**
   - 答：向量 + BM25 + 图召回三路并行 → RRF 融合 → Cross-Encoder 重排 → 截断阈值 → 送入模型。
4. **LangGraph 和 LangChain 的区别？**
   - 答：LCEL 是线性声明链，一条路走到黑；LangGraph 是状态机（图），有节点、边、共享 State，能循环、能分支、能持久化——复杂 Agent 用后者。
5. **Agent 的 ReAct 流程讲一遍。**
   - 答：模型看到问题 → 输出"思考 + 行动（工具+参数）" → 系统执行 → 结果回传 → 模型再思考 → 直到给出最终答案。
6. **SSE 与 WebSocket 区别，你各用在哪里？**
   - 答：SSE 单向推；WS 双向全双工。LLM 网关用 SSE 推 token；对话过程用 WebSocket 推状态。
7. **熔断器怎么设计？**
   - 答：数失败连续 N 次 → 打开切断请求（快速失败省时间）→ 冷却 30s 后进入半开，试探 1 个请求，成功则关。
8. **JWT 认证怎么做的？**
   - 答：登录签发（签名）→ 请求带头 → 校验签名与过期；无状态，便于水平扩展，缺点是无法主动吊销（可加黑名单）。
9. **Docker 和虚拟机区别？**
   - 答：共享宿主内核的隔离进程（镜像分层、秒级启动） vs 完全虚拟化一个内核/OS（更重更隔离）。
10. **为什么 Python 适合 AI 应用开发？你对异步编程的理解**
    - 答：生态（模型 SDK、框架）；异步：IO 密集型场景用 async/await + 事件循环，IO 等待时不阻塞 CPU，吞吐更高。

### B+. RAG 模块 · 完整追问清单（26 题，面试官视角）

> 标注：🔴 必问（几乎每场都问）｜🟡 常问（一半概率）｜🟢 加分问（问到了就是机会）
> 用法：每道题都要能用自己的话讲 1 分钟。🔴 题全部过关后再扫 🟡，最后 🟢。

**Q0. 主问题（必背）：讲讲完整的 RAG 链路——文档进来后从分块到最终回答，每一步怎么做的？**

- 我的回答记录（第一轮模拟，问题：口语口误多、漏了 Rerank 步骤）：
  - 答出：提取清洗 → 分块 → 向量化 → 存向量库；意图分析 → 三路召回（BM25 / 向量 ANN / 图关联）→ 融合排序 → Top-K → 模型回答；提了幻觉约束与标出处
  - 口误：项量（向量）、高位（高维）、最近零（最近邻）、RFF/2FF（RRF）、TopKey（Top-K）
  - 遗漏：**没提 Rerank 精排**——简历核心卖点，面试官必追
  - 重复：同一句"借助XX排序算法对各路结果加权计算"说了两遍
- 标准答案模板（背这个）：

> "RAG 整体分两个阶段。**离线建库阶段**：文档进来先提取清洗，再按策略分块，然后用向量模型转成向量，存进向量数据库。
>
> **在线检索阶段**：用户提问后，先做意图分析提取关键词；然后三路召回——BM25 做关键词检索、向量库用 ANN 最近邻做语义检索、图数据库做实体关联检索；三路结果用 RRF 融合排序；**再经过 Rerank 精排（Cross-Encoder 模型），取 Top-K 最相关的片段**；最后交给大模型，让它只基于这些片段回答，并标明出处，约束幻觉。
>
> 整体就是：建库 → 召回 → 融合 → 精排 → 生成。"

- 流程口诀：**建库 → 召回 → 融合 → 精排 → 生成**（五步，顺序不能错）
- 发音自查：向量 xiàng liàng / 高维 gāo wéi / 最近邻 lín / RRF（r-r-f）/ Top-K

**A. 建库阶段（离线）**
1. 🔴 分块策略怎么选的？chunk size 和 overlap 怎么定的？
2. 🔴 chunk 太大或太小分别有什么后果？
3. 🟡 固定大小分块 vs 语义分块 vs 父子分块，区别？
4. 🟡 用哪个 embedding 模型？为什么选它？中文效果如何？
5. 🟡 500+ 份文档入库要多久？文档更新了怎么增量入库？
6. 🟢 扫描件/表格类文档怎么处理？解析层遇到过什么坑？
7. 🟢 重复文档、脏数据怎么去重清洗？

**A 阶段 · 标准答案（整合版，背这段）**

> "建库分四步：**解析 → 清洗 → 分块 → 向量化入库**。
> 解析用文档加载器处理 PDF/Word，扫描件用 MinerU/PaddleOCR 兜底，坑是表格和低质量扫描会识别错，需要人工抽检；清洗做哈希去重、剔除过时文档。
> 分块按文档类型选——通用用递归字符分块（chunk 500、overlap 20%），长文用语义分块，要上下文完整用父子分块（小块检索、父块喂模型）；chunk 大小通过线下评测对比召回和回答质量来定。
> 向量化用千问 embedding 模型（中文好、可本地部署），存向量库。
> 增量更新用文档哈希比对：没变的跳过、变了的重建、删了的清理，不做全量。"

- 口诀：**解析 → 清洗 → 分块 → 向量化**（四个动作）
- 三种分块速记：
  - 固定大小：按字符数机械切分，实现简单，可能切断语义
  - 语义分块：embedding 算相邻句子相似度，在"语义断层"处切
  - 父子分块：大块（保上下文）+ 小块（做检索），命中小块后把父块给模型——**"检索用小、喂模型用大"**
- chunk 大小调参：500-1000 token 常用、overlap 20%-30%；太大→token 浪费+相关性稀释，太小→语义破碎；用线下评测（召回率+回答质量）定

**A4 追问 · Embedding 模型速查表（面试官问"向量维度多少"必备）**

> 面试官真实问过的点："你的词嵌入模型高维向量是多少位？"——必须能答出自己用的模型的参数量和维度。

- **Qwen3-Embedding 系列（阿里，2025.6 发布，中文最强梯队）**：
  - Qwen3-Embedding-0.6B：**0.6B 参数 / 1024 维** / 32K 上下文（支持 32-1024 自定义维度）
  - Qwen3-Embedding-4B：**4B 参数 / 2560 维** / 32K
  - Qwen3-Embedding-8B：**8B 参数 / 4096 维** / 32K（CMTEB 中文霸榜）
  - 配套 **Qwen3-Reranker**（0.6B/4B/8B）做重排序
- **通义 API 版**：text-embedding-v3（1024 维）、text-embedding-v4（64-2048 维可调，8K 长文本）
- **BGE-M3（智源 BAAI，开源）**：**568M 参数 / 1024 维** / 8K，中文社区首选，支持 dense+sparse 混合
- **OpenAI**：text-embedding-3-small（1536 维）、text-embedding-3-large（3072 维，可降维到 256/1024）
- 面试答法（如果被问）："我用的是 Qwen3-Embedding-0.6B，1024 维，开源可本地部署，中文效果好；选它也是因为和 Qwen3-Reranker 配套，检索和精排生态统一。"
- 注意：**embedding 模型（做召回）≠ reranker 模型（做精排）**——embedding 输出向量，reranker 输出相关性分数（详见下方"双塔 vs Cross-Encoder"）

**A4 追问 · 模型选型（embedding + reranker 怎么搭配）**

- Qwen3-Embedding 与 Qwen3-Reranker **同参数量一一对应成对发布**（0.6B/4B/8B），官方推荐配套用
- **衔接机制（重点）**：embedding 输出向量存库供检索；reranker 输入的是**原始文本**（问题+片段拼接），不接收向量 → 两者靠**文档 ID 衔接，不存在维度匹配问题**（embedding 1024 维 vs 4096 维，reranker 都不关心）
- 流程：向量库粗筛 Top-100 → 候选片段**文本**交给 reranker 逐条打分 → 按分取 Top-K → 喂 LLM（两层漏斗：快而粗 → 慢而准）
- BGE-Reranker（base 278M / v2-m3 568M，v2-m3 支持 8K）vs Qwen3-Reranker（0.6B/4B/8B，全系 32K 上下文，中文更强）：老牌稳妥 vs 新锐顶级
- 简历话术（用户实际用 BGE）："我用 BGE-Reranker，成熟稳定、部署轻量、中文效果好；如果硬件允许会升级到 Qwen3-Embedding-0.6B + Qwen3-Reranker-0.6B，中文更强且 32K 上下文能直接给长分块打分不截断"
- 加分句：embedding 和 reranker 是独立组件，可混搭（如 BGE-M3 召回 + Qwen3-Reranker 精排），不必同系列

**B 阶段 · 标准答案（第 8-14 题）**

**第 8 题：用户问题进来，第一步做什么？**

> "第一步是**意图分析 + Query 改写**。因为用户原始问题往往口语化、不完整、有歧义——比如只说'怎么退？'，直接拿去检索召回质量很差。先判断用户意图（查资料/问操作/闲聊），提取关键词，再做改写：**同义词扩展**（'退'→'退款流程'）、**拼写纠错**、**多轮对话指代消解**（'那这个呢'补全成完整问题）。改写后的完整 query 再进三路检索。"

- 一句话：**先改问题，再检索**——改得越完整，召回越准
- 面试补充："我们客服场景用户提问很口语，这一步不做，检索效果直接掉一截"

**第 9 题：三路检索分别是什么？各自召回多少条？**

> "三路是 **BM25 关键词检索、向量语义检索、图数据库实体关联检索**。配置上我每路召回 Top-50，合并去重后剩 Top-20，再过 Rerank 精排取 Top-5 喂给模型。"

- 数字口径（背这个）：**每路 Top-50 → 融合去重 Top-20 → 精排 Top-5**（50-20-5）
- 为什么不是越多越好：召回多→噪声大、融合和精排成本高；太少→漏召回。50-20-5 是性价比平衡点
- 面试官问"为什么 50"：答"500+ 文档、几万 chunk 的规模下，每路 50 能覆盖绝大多数相关片段，再多边际收益下降"

**第 10 题：为什么混合检索比纯向量检索好？向量检索短板？**

> "混合检索=**字面精确命中 + 语义泛化**互补。BM25 对型号、编号、专有名词这类**精确标识符**命中强（比如查 'XK-100 型号'）；向量检索对**同义词、换说法**命中强（'退钱'和'退款'是同一个意思）。单用向量检索的短板不是速度——有 ANN 索引很快——**短板是精确匹配弱**：型号、编号、冷门专业词，语义向量可能匹配不到；单用 BM25 的短板才是**只能字面匹配**，同义词全漏。"

- 记忆：**BM25 抓"字"，向量抓"意"**；混合=两手都抓
- 面试官追问"向量检索慢不慢"：答"不慢，向量库用 HNSW 这类 ANN 索引，毫秒级返回；它的短板在精确词匹配，不在速度"

**第 11 题：BM25 是什么？和 TF-IDF 区别？**

> "BM25 是**关键词检索的排序算法**。核心思想：词在文档里出现越多越相关（词频），但**越常见的词越不重要**（逆文档频率，比如'的''是'权重很低），同时**文档越长越吃亏**（长度归一化，防止长文档靠字数堆词频占便宜）。和 TF-IDF 的区别：TF-IDF 是基础版（词频×逆文档频率）；BM25 是改进版，多了两个修正——**词频饱和**（词出现 10 次和 100 次的区分度递减，k1 参数控制）和**长度归一化**（b 参数控制）。工程上 BM25 效果普遍优于 TF-IDF。"

- 一句话：**TF-IDF = 词频 × 稀有度；BM25 = TF-IDF + 词频饱和 + 长度惩罚**
- 公式别背，理解三个因子即可：词频↑相关、太常见↓权重、太长↓惩罚

**第 12 题：ANN 和暴力检索的区别？HNSW？**

> "暴力检索是把 query 和库里**每一个向量**逐一算相似度，O(N)，准确但慢；ANN（近似最近邻）不逐一比较，用索引结构**只和少量候选**算，O(log N)，牺牲一点精度换毫秒级速度。HNSW 是常用索引：**分层图结构**，上层稀疏负责粗粒度快速跳转（先定位大致区域），下层稠密负责精确定位——像先看地图定城市，再进街区找门牌。"

- 纠正：**余弦夹角是两种检索共同的打分方式，不是 ANN 的区别**——区别只在"怎么找"，不在"怎么算分"
- 面试答法："我们几万 chunk，暴力检索每次几万次计算，ANN 毫秒级返回，体验差别巨大"

**第 13 题：GraphRAG 怎么做？解决什么问题？**

> "流程：**实体抽取 → 关系抽取 → 构建知识图谱 → 社区发现 → 社区摘要 → 检索时沿图扩展**。具体：用 LLM 从文档抽出实体（人、系统、组件）和它们的关系，存图数据库；图算法把关系紧密的实体聚成**社区**，LLM 给每个社区生成摘要；用户提问时先定位相关实体，沿关系边扩展，再结合社区摘要回答。
> 它解决的问题：**向量检索找'文本长得像的'，GraphRAG 找'语义有关联的'**——比如文档 A 说'系统 X 依赖 Y'，文档 B 说'Y 已废弃'，两篇文本毫无相似词，向量检索找不到，但图里 X—Y 相连，一查就通。它擅长**跨文档隐性关联、多跳推理、全局性提问**（'整个系统架构是什么'）。"

- 一句话：**向量检索找相似文本，图谱检索找关联关系**
- 代价（加分句）：建图成本高，所以只对高频/核心知识建图谱，不做全量

**第 14 题：召回质量差怎么补救？多轮对话怎么处理？**

> "补救从轻到重：①**Query 改写**（同义词扩展、纠错、补全）；②**调分块策略**（chunk 太大召回粒度粗，改小或换语义分块）；③**加大召回数量**；④**调混合检索权重**；⑤**Rerank 精排兜底**；⑥换更强的 embedding 模型。
> 多轮对话：**指代消解**——让 LLM 把'历史对话 + 当前问题'改写成一个独立的完整 query（把'它''那个'补全），再走正常检索，保证每一轮检索都是完整问题。"

- 一句话：**先改 query，再调参数，最后换模型**——从成本低到高
- 多轮对话答法：**"先改写补全，再检索"**——和第一题的意图分析是同一个动作的延伸

**C. 融合阶段**

16. 🟡 三路召回结果有重叠，怎么去重？

**C 阶段 · 标准答案（15-16 题）**

**第 15 题：RRF 公式？为什么 k 取 60？**

> "RRF 是**倒数排名融合**（Reciprocal Rank Fusion）：对每个候选文档，把**三路召回里它各自的名次取倒数相加**，得分越高排名越靠前。公式是 score(d) = Σ 1/(k + rank_i)，rank_i 是文档在第 i 路的排名。k 是一个平滑常数，经典做法取 **60**——作用是**压低第一名对后续的碾压**：排名第 1 得 1/61≈1.6%，排名第 10 得 1/70≈1.4%，差距很小，**保证在某一路上排名靠后的文档也有机会进精排**。k 越小第一名的优势越大，k=60 是论文里反复实验出的稳定值。"

- 公式不用默写，理解三要素：**每路取倒数 → 相加 → k 平滑**
- 面试官问"为什么不用加权分数融合"：答——**三路的分数尺度完全不同**（BM25 的关键词分值、余弦相似度、图关联度），直接加权必须先把分数归一化、还要调三路权重，工程上很麻烦；RRF **只用名次、不用分数**，天然屏蔽尺度问题，零调参、鲁棒——这是它最大的优势

**第 16 题：三路召回结果重叠怎么去重？**

> "按**片段 ID / 内容哈希**去重：同一个片段被多路召回时只保留一条。合并后以唯一 ID 建索引，重复的只留下**名次最高的那条**（保留它在各路的排名用于 RRF 计算）。另外还要做一步**近重复判断**——内容高度相似（散落各处的同一段话）用相似度阈值合并，防止喂给模型的片段冗余。"

- 一句话：**ID 去重防重复，相似度去重防冗余**

17. 🔴 Rerank 用什么模型？为什么选它？

19. 🟡 Rerank 输出是什么？怎么排序取 Top-K？
20. 🟢 Top-K 取多少？取太大/太小的权衡？（token 成本 vs 质量）

**D 阶段 · 标准答案（Rerank 原理，重点纠正）**

> "Rerank 用 BGE-reranker（Cross-Encoder 架构）。原理和 embedding 完全不同：**不是把问题和文档转成向量算相似度**，而是把 query 和每个候选片段**拼成一段文本**，整体送进 Transformer，让两者的 token 在自注意力里充分交互，最后用一个分类头输出一个 0-1 的相关性分数。分数越高越相关，按分数排序取 Top-K。"
>
> "因为是拼接全文交互，精度比向量相似度高，但计算量大、速度慢，所以**只对召回阶段粗筛出来的 Top-100 左右做精排**，不对全库做——全库用向量 ANN 粗筛，候选用 Cross-Encoder 细排，这是两层漏斗。"

- **双塔（Bi-Encoder，召回用）**：query 和 doc 各自独立编码成向量 → 离线预计算好 → 在线算余弦相似度。快，但 query 和 doc 在编码时**互不交互**，精度有限。
- **Cross-Encoder（精排用）**：query+doc **拼接成一个序列**共同编码，token 级交互充分 → 输出分数。慢，但准。**不产出向量，只产出分数。**
- 用户误区纠正（面试千万别这么说）：Rerank 不是"当时把问题和文档转成向量再算一遍"——那就和召回阶段没区别了。Rerank 靠的是**拼接交互 + 打分**，不是向量计算。
- 发音自查：精排 jīng pái（不是"金牌"）、Rerank（rī-ræŋk）、BGE（b-g-e，不是 PGE）
- 对比记忆：**召回 = 向量相似度（双塔），精排 = 拼接打分（Cross-Encoder）**——一个"快而粗"，一个"慢而准"

**Rerank 原理 · 精简速记（30 秒回忆版）**

> 一句话：**问题 + 文档拼成一段文本 → 一起进 Transformer 做自注意力交互 → 输出一个相关性分数**。
> 三步：①拼接（query [SEP] doc）→ ②交互（token 级自注意力）→ ③打分（0-1 分数排序取 Top-K）。
> 记三个"不"：**不转向量、不算相似度、不对全库**（只对召回候选 Top-100 精排）。

**E 阶段 · 标准答案（21-23 题）**

**第 21 题：怎么把片段组织进提示词？引用出处怎么标注？**

> "提示词结构固定三段：**系统角色 + 检索片段 + 用户问题**。检索片段每条带编号和出处标签（如 [1] 来自《产品手册.pdf》第三章），回答时要求模型按编号引用（'根据资料[1][2]…'）。同时明确规则：只能基于片段回答，片段的原文里有什么才能说什么。"

- 记忆：**片段带编号、答案带引用、只答片段内**

**第 22 题：幻觉怎么约束？无关时怎么办？**

> "幻觉三条防线：①**规则约束**——提示词里写明'只能基于检索内容回答，不得编造'；②**引用强制**——要求每个结论都标注片段编号，模型没法引用就不敢编；③**拒答机制**——如果检索结果与问题完全不相关，直接回答'知识库中没有找到相关信息'，而不是硬答。我做了一套打分兜底：检索相关性低于阈值时直接触发拒答，不把垃圾片段喂给模型。"

- 拒答按钮：**相关性低于阈值 → 拒答**，这是加分设计

**第 23 题：上下文超长怎么办？**

> "三个手段：①**只喂精排后的 Top-K**，前面链路已经压缩过了；②**分段摘要**——对超长片段先让模型压缩成要点再拼入上下文（衔接项目二做过的 Token 管理）；③**动态裁剪**——按片段权重丢弃低相关的，预算不够时优先保头部。"

- 一句话：**先精排压缩、再摘要压缩、最后按权重裁剪**

**F. 评估与优化**
24. 🔴 怎么知道你的 RAG 效果好？具体看什么指标？（RAGAS 四个指标）
25. 🟡 用户反馈"答案不对"，你怎么排查是检索问题还是生成问题？
26. 🟢 回答延迟怎么优化？缓存怎么做？

**F 阶段 · 标准答案（24-26 题）**

**第 24 题：怎么评估 RAG 效果？RAGAS 指标？**

> "用 **RAGAS 四个指标**量化：①**Faithfulness 忠实度**——回答内容有多少能在检索片段中找到依据（防幻觉，最关键）；②**Answer Relevance 答案相关性**——回答和问题对不对得上；③**Context Relevance 上下文相关性**——检索出来的片段本身和问题相关度（召回质量）；④**Context Recall 上下文覆盖率**——问题所需的信息有多大比例被检索出来了（对应我项目的 91.8% 覆盖率）。每个指标对标注集跑分，分数化了才好调优对比。"

- 记忆四件套：**忠实度（别编）、相关度（对得上）、上下文相关（召回好）、覆盖率（召回全）**

**第 25 题：用户说答案不对，怎么排查？**

> "**二分定位法**：把检索片段直接丢给模型让它单独生成——如果生成质量好，说明模型没问题，问题在**检索端**（查查召回片段对不对）；如果生成还是不对，问题在**生成端**（提示词/模型）。再往下：检索端看反馈的片段相关性分数，生成端看输出是否忠实于片段。先切一半，再查源头，不拍脑袋。"

- 口诀：**先手动喂片段给模型 → 模型好则查检索，模型差则查生成**

**第 26 题：回答延迟怎么优化？缓存怎么做？**

> "四层优化：①**缓存**——相同/相近问题命中直接返回（query 归一化后走缓存），模型请求和检索结果都能缓存，热点问题命中率最高；②**并发**——三路召回并行跑，汇总阶段才汇合；③**精排降量**——Top-100 降到 Top-50，省 Rerank 时间；④**流式输出**——首 token 快出，用户先看到字在动。缓存注意失效：知识库更新时相关缓存要失效。"

- 记忆：**缓存、并发、减量、流式**——延迟四板斧

### C. 项目一深挖：OmniAgent（多智能体 RAG 知识库）

1. **500+ 份文档怎么入库的？重跑怎么办？**
   - 答：解析（PDF/Word）→ 清洗 → 分块 → embedding → 存向量库；增量入库按文档指纹/时间戳跳过未变文档；支持全量重建。Alembic 管 schema 变更，迁移脚本兼容旧数据。
2. **三路混合检索具体实现？**
   - 答：向量检索 Top-K + BM25 关键词 Top-K + 图检索（实体关系链）Top-K → 合并去重 → RRF 融合。
3. **重排序用什么模型？**
   - 答：Cross-Encoder 类 reranker（把 query 和候选文档一起编码打分），在召回 Top 50 上精排取 Top 5；比双塔准但慢，所以只精排不改过路全部。
4. **LangGraph 里定义了哪些节点？**
   - 答：意图识别 → 工具路由 ↔ Supervisor → 检索/SQL/代码 Worker → 结果合并 → 生成；重点说出一条真实调用路径（如"请查上月销售额"→路由到 SQL Worker → 结果转成知识库答案）。
5. **Supervisor 怎么决定分给哪个 Worker？**
   - 答：让模型输出结构化工具选择（LLM 决策 + 参数）→ 匹配工具注册表 → 白名单拦截非法工具；复杂任务再拆子任务。
6. **LangMem 存的什么？**
   - 答：会话历史（短期）+ 用户偏好/长期事实（向量化落库）；超长对话自动摘要归档节省上下文。
7. **效果怎么量化？**
   - 答：线下人工抽样评测召回与答案正确率；线上记录用户追问率/无用检索率；计划接入 RAGAS 自动评估（如已接入就讲指标）。
8. **监控了什么？**
   - 答：QPS、P95 延迟、token 消耗、链路错误率、检索命中分布；Prometheus + Grafana。

### 项目二深挖：LLM Gateway（统一模型网关）

1. **模型注册表怎么保证线程安全？**
   - 答：注册表用锁（如 rwlock）保护读写；JSON 文件兜底持久化 + 启动时加载 + 定时落盘。
2. **故障转移优先级怎么设计？**
   - 答：用户显式指定模型 → 未指定则按 priority 列表顺序尝试 → 健康探测（定期 ping）过滤不可用后端 → 失败切换。
3. **速率限制怎么做的？**
   - 答：令牌桶/滑动窗口按 API Key 维度限流；超过返回 429，客户端可退避重试。
4. **为什么用"无 tokenizer 的 Token 估算"？**
   - 答：服务器端免 tokenizer 库依赖（轻量），按中文字符/英文单词加权近似估算 token，用于动态限制 max_tokens 防止超上下文。精度不如 tokenizer 但不影响使用。
5. **覆盖 91.8% 都测了什么？**
   - 答：单元（路由决策、熔断状态机、令牌桶边界）+ 集成（真实模型后端 mock、流式拼接）+ 回归；覆盖边界（熔断临界、限流 429、上下文超长截断）。

### 6. 场景设计 / 系统设计（高频）

1. **10 万份文档做企业知识库，怎么架构？**
   - 答：解析服务 + 索引分片（向量分片 + 元数据过滤）+ 混合检索 + Rerank 服务 + 缓存 + LLM 流式；关注成本（embedding 量）、延迟（检索耗时）、更新策略（增量）。
2. **RAG 准确率怎么提升？**
   - 答：分块调优 > 混合检索 > Rerank > 提示词约束引用 > 人工反馈闭环（把用户纠正如模型权重）；每步都可量化评测。
3. **模型 API 挂了怎么处理？**
   - 答：熔断 + 降级备选模型 + 重试退避 + 超时兜底文案 + 告警。
4. **上下文窗口快满了怎么办？**
   - 答：摘要压缩 / 丢弃低权重历史 / 目录映射（章节头引用）——对标"Token 管理"经验。
5. **多 Agent 和单 Agent 怎么选？**
   - 答：任务被拆解、每步需要不同工具/不同领域模型/并行 → 多 Agent；简单线性任务单 Agent 更快更稳。多 Agent 有额外延迟和协调复杂度，默认先用单 Agent。

## 七、快速彩排 · 完整模拟面试问答（昨晚整场重现）

> 用法：昨晚就是从第 1 题一路连问到 HR 的。每道题先努力自己答，再对照标准答案。**全答得出来就是今晚稳了。** 🔴=必考（几乎每场） 🟡=常考 ⚡=加分
> 对应章节：每题标注了详细答案的出处，记不住就翻过去背。

### 第 1 轮 开场 · 自我介绍（🔴）

**Q1. 先简单介绍一下你自己吧。**
- 定型版见「四」：4年经验/数据背景 → 2024 转 LLM → 项目一（RAG 知识库 + 多智能体）→ 项目二（统一模型网关）→ 独立完成需求到上线。
- 要点：控制 1 分钟；结尾固定"整体情况就是这样。"；只抛钩子不展开（500+ 文档、熔断降级留追问）。

**Q2. 你简历写知识库接了 500 多份文档，讲讲完整的 RAG 全链路——文档进来之后从分块到最终回答，每一步怎么做的？**
> 标准答案（完整版见「二、B+ Q0「）：解析→清洗 →分块 →向量化建库 → 意图分析 → 三路召回（BM25/向量 ANN/图关联）→ RRF 融合 → Cross-Encoder 精排 → TopK 喂模型 → 片段答 + 标出处。整体：**建库 → 召回 → 融合 → 精排 → 生成**（五步顺序不能错）。

**Q3. （常见顺连）你分块策略怎么选？chunk size 和 overlap 怎么定？（🟡 必背：「二、B+ 第 1-3 题」）
> 按类型选：通用长文用递归字符分块（chunk 500/overlap 20%），长文用语义分块，需上下文完整用父子分块（小块检索、父块喂模型）；chunk 大小不拍脑袋，用线下评测（召回率+回答质量）定。记忆：**固定=机械切、语义=断在断层、父子=检索小喂大大**。

**Q4. Rerank 为什么不用向量再算一遍？（🔴 上次口语卡住的点）**
> Rerank 用 Cross-Encoder：把 query+文档**拼成一段文本**整体送进 Transformer，token 级交互后输出一个 0-1 相关性分数——不是转向量算相似度，是"拼接→交互→打分"。所以只对召回 Top-100 精排，候选才是它的阶段。记忆：**拼→交→打**。

### 第 2 轮 RAG 细节追问（🔴 项目一挖到底）

**Q5. 三路召回各召回多少条？为什么混合比纯向量好？**
> 每路 Top-50 → 合并去重 Top-20 → 精排取 Top-5。BM25 抓"字"（型号、编号、专有名词），向量抓"意"（同义词、换说法）；单用向量检索的短板不在速度（有 ANN 毫秒级），而在**精确词匹配弱**——型号、冷门词语义向量可能匹配不到。记忆：**BM25 抓字、向量抓意，混合=两手都抓**。

**Q6. BM25 和 TF-IDF 区别？（🟡 见「二、B+ 第 11 题」）**
> TF-IDF = 词频 × 逆文档频率（基础版）；BM25 = TF-IDF + **词频饱和**（k1 参数：出现 10 次和 100 次区分度递减）+ **长度归一化**（b 参数：长文档惩罚）。工程上 BM25 普遍优于 TF-IDF。记忆：**TF-IDF=词频×稀有度；BM25=TF-IDF+饱和+长度惩罚**。

**Q7. HNSW 为什么比暴力检索快？**
> 暴力检索是 O(N) 逐一算相似度；ANN 用索引只和少量候选比，O(log N) 毫秒级。HNSW 是**分层图结构**：上层稀疏快速跳到大致区域，下层稠密精确定位——先看地图定城市，再进街区找门牌。注意：**余弦夹角是两种方式共同的打分方法，区别只在"怎么找"，不在"怎么算分"**。

**Q8. GraphRAG 做了什么？解决什么？（🟡）**
> 流程：实体抽取 → 关系抽取 → 建知识图谱 → 社区发现 → 社区摘要 → 检索时沿图扩展。解决的问题：向量检索找"**文本长得像的**"，GraphRAG 找"**语义有关联的**"——比如文档 A 说"系统 X 依赖 Y"、文档 B 说"Y 已废弃"，两篇文本毫无相似词，但图里 X—Y 相连一查就通。擅长跨文档隐性关联、多跳推理、全局性问题（"整个系统架构是什么"）。代价：建图成本高，只对核心高频知识建图。

**Q9. RRF 为什么 k=60？（🟡）**
> RRF = 倒数排名融合：把候选文档在**每一路的名次取倒数再相加**，公式 score(d) = Σ 1/(k + rank_i)。k=60 是论文实验出的稳定平滑值，作用是**压低第 1 名的碾压优势**（第 1 名 1/61、第 10 名 1/70，差距很小），让某一路排名靠后的候选也有机会进精排。为什么不用加权分数融合？——三路分数尺度完全不同（BM25 分/余弦相似度/图关联度），加权要先归一化再调三路权重，麻烦；RRF 只用名次、天然屏蔽尺度问题、零调参。

**Q10. 幻觉怎么防止？（🔴）**
> 三层防线：①**规则约束**——提示词写明"只能基于检索内容回答，不得编造"；②**引用强制**——每个结论必须标注片段编号 [1][2]，模型不敢编；③**拒答机制**——检索相关性低于阈值时直接拒答"知识库中未找到相关信息"，不硬答。我额外做了打分兜底：低于阈值直接触发拒答，垃圾片段不喂给模型。

### 第 3 轮 · Agent / LangGraph（🔴 项目一核心）

**Q11. LangGraph 和 LangChain 什么区别？为什么用它在项目一？**
> LCEL 是**链式线性**声明，一条路走到底；LangGraph 是**状态机（图）**：有节点、边、共享 State，支持循环、分支、持久化。我的 OmniAgent 有多个 Worker 节点 + Supervisor 路由，需要状态流转和分支决策，链式 LCEL 做不到，所以选 LangGraph。

**Q12. 你定义了哪些节点？走一条真实路径。**
> 意图识别 → 工具路由（Supervisor）→ 检索 / SQL / 代码 Worker → 结果合并 → 生成。真实路径示例："请查上月销售额" → 路由到 SQL Worker → 查数据库 → 结果转成知识库风格答案。

**Q13. Supervisor 怎么决定分给哪个 Worker？**
> 让模型输出**结构化工具选择**（工具名+参数）→ 匹配工具注册表 → 白名单拦截未注册工具；复杂任务再拆成子任务。记忆：**模型选择 → 注册表匹配 → 白名单拦截**。

**Q14. LangMem 存什么？会污染吗？**
> 存两部分：**会话历史**（短期）+ **用户偏好/长期事实**（向量化落库）；超长对话自动摘要归档节省上下文。追问防坑："长期记忆会不会污染？——长期事实做置信度加权过滤，低置信度不写入；设置只读白名单，防止错误事实固化。"

### 第 4 轮 · 检索评估与优化（🟡 常考）

**Q15. RAGAS 四个指标？（🔴）**
> ①**Faithfulness 忠实度**——回答能在检索片段里找到依据（防幻觉，最关键）；②**Answer Relevance 答案相关性**——回答和问题对得上；③**Context Relevance 上下文相关性**——检索出来的片段本身和问题相关（召回质量）；④**Context Recall 覆盖率**——问题所需信息有多大比例被检索出来（对应我的 91.8% 覆盖率）。量化了才好调优。

**Q16. 用户说"答案不对"，你怎么排查？**
> **二分定位法**：把检索片段单独丢给模型生成——如果生成质量好，说明问题在**检索端**（看召回片段对不对）；如果生成还是不对，问题在**生成端**（提示词/模型）。先切一半，再查源头，不拍脑袋。

**Q17. 回答延迟怎么优化？**
> 四板斧：①**缓存**——相同/相近问题直接命中返回；②**并发**——三路召回并行跑；③**精排降量**——Top-100 降到 Top-50，省 Rerank 时间；④**流式输出**——首 token 快出，用户先看到字在动。

### 第 5 轮 · 实时通信四连问（🔴 重点彩排过，见下 Q18-21）

**Q18（双向 vs 单向）：项目一用 WebSocket 推 Agent 思考过程（双向），项目二用 SSE 推 token（单向），前端对话的时候一个双向一个单向，不矛盾吗？**

> "不矛盾。"双向/单向"说的是**连接的能力**，不是'对话就必须用双向'。选型只看一件事：**流中间需不需要交互**。项目一是 Agent 对话，思考过程里用户随时要打断、要确认工具调用、要换问法——这些动作都发生在流中间，客户端必须能随时再发消息，所以用 WebSocket 双向。项目二只是下游应用发一次请求、网关流式返回 token、结束，中间没有任何交互需求，SSE 单向足够，而且基于 HTTP、自带自动重连，更轻量。"

- 一句话记忆：**双向还是单向，取决于流中间需不需要交互。**

**Q19（深挖）：浏览器和后端之间是 WebSocket 双向，但后端调模型用的是 SSE——那用户中途发的中断消息，模型那边根本收不到啊？**

> "模型**不需要'收到消息'，它只需要'连接断掉'**。用户点停止 → 中断消息走 WebSocket 到后端 → 后端**断开与模型的那条 SSE 请求连接** → vLLM 检测到客户端断连，自动终止生成 → 已经吐出来的半截 token 由后端丢弃、不回给前端。SSE 的特性就是'服务端推、断连即停'，正好为流式中断而生。所以中断靠'断连'实现，不是靠'发消息'。"

- 三层链路图（能画出来就赢了）：

```
浏览器 ←— WebSocket 双向 —→ 后端 ←— SSE 单向 —→ 模型(vLLM)
 上行：发消息/打断/确认工具        下行：token 流（模型不接收指令）
 下行：思考过程/工具状态/回复       断连 = 停止信号
```

- 一句话记忆：**WebSocket 管交互，SSE 管推流，断连管停止——各司其职。**

**Q20（定位）：那 WebSocket 到底用在哪里？**

> "WebSocket 用在**前端浏览器和后端网关之间**这一层，不在后端和模型之间。它承载的是人机交互：上行是用户发消息、点停止打断、确认/拒绝工具调用；下行是 Agent 思考过程、正在调用哪个工具、工具结果、最终回复；还有心跳保活。后端和模型之间是另一条连接，只管模型往外吐 token，单向 SSE 正好。"

- 一句话记忆：**两层连接各管一段——人机交互走 WebSocket，模型推流走 SSE，互不重叠。**

**Q21（选型）：什么场景用 WebSocket，什么场景用 SSE？**

| 场景 | 选型 | 原因 |
|---|---|---|
| Agent 对话（可打断、工具确认） | WebSocket | 流中间要双向交互 |
| 模型 token 流式返回 | SSE | 单向下发 + 断连即停 |
| 服务端通知/推送（新闻、告警、进度） | SSE | 单向、自动重连、基于 HTTP 简单 |
| 聊天 IM / 协同编辑 / 游戏 | WebSocket | 高频双向消息 |

- 一句话记忆：**有来有回、流中要插话 → WebSocket；只推不改、发一次收一次 → SSE。**

### 第 6 轮 · 项目二网关深挖（🟡 简历第二卖点）

**Q22. 熔断器怎么设计？（🔴 简历参数）**
> 三态：CLOSED 正常 → 连续失败 5 次 → OPEN 直接拒绝（快速失败）→ 冷却 30 秒 → HALF_OPEN 放行 1 个试探 → 成功转 CLOSED，失败再开。记忆：**5 次失败熔断 / 30 秒半开**。

**Q23. 故障转移优先级怎么设计？**
> 用户显式指定 → 未指定按 priority 列表顺序尝试 → 健康探测过滤不可用后端 → 失败自动切换下一个。

**Q24. 速率限制怎么做的？**
> 令牌桶 / 滑动窗口按 API Key 维度限流；超过返回 429，客户端退避重试。

**Q25. 为什么用"无 tokenizer 的 Token 估算"？**
> 服务端免 tokenizer 库依赖（轻量），按中文字符/英文单词加权近似估算，用于动态限制 max_tokens 防止超上下文。代价是精度低，换来轻量快速。

**Q26. 覆盖 91.8% 都测了什么？**

## 八、关键名词深度知识（面试深挖版）

> 用法：面试官问名词时，先给"一句话定义"站稳，再往下扩展 2~4 点原理，最后用"面试加分词"收尾——这是"懂原理"和"背概念"的区别。手机上看：每节 30 秒能过一遍。

### 1. WebSocket

- **一句话定义**：基于 TCP 的全双工通信协议，连接建立后客户端和服务端**都能随时主动发消息**。
- **扩展**：
  - 握手靠 HTTP 升级（`Upgrade: websocket` + `Connection: Upgrade` + Sec-WebSocket-Key，服务端算 SHA-1 返回 Sec-WebSocket-Accept），握手成功后同一条 TCP 连接上双向收发，协议已不是 HTTP。
  - 消息以**帧**为单位传输：文本帧、二进制帧、控制帧（ping/pong 保活、close 关闭）——帧协议天然解决"粘包"问题。
  - **心跳**：服务端定时发 ping，客户端回 pong，用来快速发现死连接（TCP 断了不一定立刻知道），超时未回 pong 判定断开、清理资源、触发重连。
- **面试加分词**："WebSocket 和 HTTP 什么关系？"→"它靠 HTTP 握手升级建立，之后是独立的双向长连接协议；HTTP 是请求-响应模式，WebSocket 是事件驱动推送模式。"

### 2. SSE（Server-Sent Events）

- **一句话定义**：基于 HTTP 的**单向**服务端推送，浏览器用 EventSource 接收，服务端按 `text/event-stream` 格式持续下发。
- **扩展**：
  - 消息由字段组成：`data:`（内容）、`event:`（事件类型，默认 message）、`id:`（消息 ID）、`retry:`（重连间隔毫秒）；多条 data 拼成一条消息，空行分隔。
  - **自动重连**：连接断开浏览器自动重连；带 `id` 的消息配合 `Last-Event-ID` 请求头，服务端能续传断点，不丢消息。
  - 对比 WebSocket：SSE 基于 HTTP，天然过防火墙/代理，无需额外协议配置；WebSocket 是独立协议，部分代理中间件要特殊配置。
- **面试加分词**："SSE 为什么适合模型流式输出？"→"模型本来就是单向下发 token，SSE 单工正好匹配；自带重连省事；客户端断开服务端能感知，正好做断连即停。"

### 3. 单工 / 半双工 / 全双工

- **一句话定义**：通信方向的三种模式——单工只能一方发，半双工两边都能发但不能同时，全双工两边同时收发。
- **扩展**：
  - 单工：SSE（服务端 → 客户端，只能一个方向）。
  - 半双工：对讲机；**HTTP 请求-响应本质就是半双工**——一个请求对应一个响应，期间不能并发另一对。
  - 全双工：打电话；WebSocket。
- **面试加分词**："SSE 是单工、HTTP 请求响应是半双工、WebSocket 是全双工——选型前先想清楚业务需要哪种方向性，方向定错，协议选什么都不对。"

### 4. 流式输出（Streaming）与 TTFT

- **一句话定义**：模型边生成边下发，首 token 先到，用户不用干等整段生成完。
- **扩展**：
  - 关键指标 **TTFT（Time To First Token，首 token 延迟）**——从发起请求到收到第一个 token 的时间，直接决定"开始打字"的体感；首 token 快，用户感知就快，总延迟被掩盖。
  - 实现：OpenAI 兼容接口 `stream=true` → 服务端按 SSE 逐 chunk 下发增量（`choices[0].delta.content`）→ 前端逐段 append。
- **面试加分词**："为什么 LLM 必须流式？"→"长回答非流式要等几秒到几十秒整段返回，用户以为卡死；流式几百毫秒出首 token，体验完全不同。网关做流式还有个好处：边收边透传，首 token 延迟不叠加。"

### 5. 断连即停（客户端断开 → 服务端停止生成）

- **一句话定义**：推理服务检测到请求方断开连接，主动终止该次生成，释放显存/算力。
- **扩展**：
  - vLLM 等推理框架在流式响应时监听连接状态，客户端断开（用户打断/网络断）即取消生成，避免无效计算浪费 GPU。
  - 网关层完整链路：前端 WebSocket 收"停止" → 网关断开到模型的请求 → 模型侧触发断连取消 → 半截 token 丢弃。
- **面试加分词**："用户打断的链路是'WebSocket 停止消息 → 网关断连 → 模型取消生成 → 半截 token 丢弃'，三层协作——不是把停止消息传给模型，模型只认断连。"

### 6. 心跳机制（Heartbeat）

- **一句话定义**：周期性发送探测消息确认连接存活。
- **扩展**：
  - TCP 层自带 keepalive，但默认探测周期长达小时级、不实用；**应用层心跳**（WebSocket ping/pong）用于快速发现死链。
  - 发现断开后的处理：前端显示重连中 → 自动重连（常用指数退避）→ 恢复后补发期间的消息。
- **面试加分词**："我们 WebSocket 服务端每 30 秒 ping 一次，客户端 pong 超时即判定断开、清理连接资源；断线后客户端指数退避重连，避免打爆服务端。"

### 7. 轮询 / 长轮询 / SSE / WebSocket 演进（被问"为什么不用轮询"必备）

- **轮询**：客户端定时问"有新消息吗"——延迟取决于轮询间隔，大量空请求浪费资源。
- **长轮询**：服务端没消息就挂住请求，有消息才返回，客户端收到后立刻再发起——比轮询实时，但每次都重新建 HTTP 连接，开销仍在。
- **SSE**：一条 HTTP 长连接持续推，服务端有事才发，连接复用、接近零延迟。
- **WebSocket**：双向长连接，适合有来有回的交互。
- 一句话记忆：**从轮询到 WebSocket，本质是"连接复用 + 从客户端拉改为服务端推"。**

### 8. 连接复用 / keep-alive（顺带考点）

- **一句话定义**：HTTP 请求-响应后不立即断开 TCP，复用同一连接发后续请求。
- **扩展**：
  - HTTP/1.1 keep-alive 串行复用；HTTP/2 多路复用（Multiplexing）一条连接并行多个流。
  - SSE 长期占用一条连接，所以网关对 SSE 路径的连接数、空闲超时要单独配置，不能按普通请求的超时掐断。
- **面试加分词**："SSE 长连接不能被网关的空闲超时误杀，我们给 SSE 路径单独配了更长的超时和连接数上限。"

### 9. Embedding（词嵌入）与向量检索

- **一句话定义**：把文本转成固定长度的稠密向量，语义相近的文本在向量空间里距离也近。
- **扩展**：
  - 训练目标：让"退款"和"退钱"这类语义相近文本的向量夹角小（余弦相似度高），是语义检索的基础。
  - **双塔（Bi-Encoder）**：query 和 doc 各自独立过模型成向量，离线预计算，在线算相似度——快但互不交互，用于召回阶段。
  - 与 reranker 的区别：embedding 输出向量供索引检索；reranker 输出相关性分数（0-1），不产向量。两者通过文档 ID 衔接，不存在维度匹配问题。
- **面试加分词**："召回阶段快而粗，用向量相似度筛 Top-100；精排阶段慢而准，用 Cross-Encoder 对拼好的文本打分——两层漏斗。"

### 10. ANN / HNSW（向量索引）

- **一句话定义**：近似最近邻搜索——牺牲一点精度，换毫秒级检索速度。
- **扩展**：
  - 暴力检索 O(N) 逐一遍历，ANN 用索引结构只和少量候选算，O(log N)。
  - HNSW = 分层可导航小世界图：上层稀疏连接负责粗粒度快速跳转，下层稠密负责精确定位，类似"先定城市再看地图"。
  - 余弦相似度是打分方式，ANN 解决的是"怎么找候选"，两者不是一回事。
- **面试加分词**："几万 chunk 全量暴力检索每次几万次计算，HNSW 毫秒级返回。"

### 11. BM25 与 TF-IDF

- **一句话定义**：关键词检索排序算法，衡量文档与 query 的字面相关度。
- **扩展**：
  - TF-IDF = 词频 × 逆文档频率：词出现得多相关，太常见（"的""是"）降权。
  - BM25 在 TF-IDF 上加了两个修正：**词频饱和**（k1 参数，出现 10 次 vs 100 次的区分度递减）与**长度归一化**（b 参数，防止长文档靠堆字数占便宜）。
  - 两者不管语义，只管字面——这是混合检索要和向量互补的原因"BM25 抓字、向量抓意"。
- **面试加分词**："型号、编号、专有名词这类精确标识符，BM25 命中远强于语义向量。"

### 12. RRF（倒数排名融合）

- **一句话定义**：把多个检索结果按排名融合排序，不关注分数只看名次。
- **扩展**：
  - 公式 score(d) = Σ 1/(k + rank_i)：每条候选在每路的排名取倒数相加。
  - k 一般取 60，是论文实验出的平滑值——压制第 1 名碾压优势，让每路靠后的候选也有机会进精排。
  - 优势：三路分数尺度不同（BM25 分、余弦、图关联度）直接加权要归一化调参，RRF 只用名次，天然屏蔽尺度差异。
- **常见追问**："为什么不用加权分数融合？"→ 见上，**只用名次、零调参、鲁棒**。

### 13. Rerank / Cross-Encoder

- **一句话定义**：对召回结果逐条精排的环节，query+doc 拼接后让模型交互打分。
- **扩展**：
  - Cross-Encoder 把 query 和每个候选**拼成一段文本**（含 [SEP] 分隔），整体进 Transformer，token 间自注意力充分交互，输出 0-1 分数。不转向量、不算余弦，只产分数。
  - 精度比双塔高、速度慢，所以只精排 Top-100 候选，不对全库做。
  - 记忆：**拼 → 交互 → 打分**；"Rerank 不是再算一遍向量"——那是老毛病。
- **面试加分词**："召回粗筛、精排细分，两层漏斗是标准的 RAG 架构。"

### 14. 知识图谱与 GraphRAG

- **一句话定义**：把实体和关系抽成图谱（节点=实体、边=关系），检索时沿图扩展。
- **扩展**：
  - 流程：LLM 抽取实体关系 → 存图数据库 → 社区发现（联系紧密实体聚簇）→ LLM 为每社区生成摘要 → 查询时定位实体沿边扩展。
  - 解决向量检索搞不定的问题：跨文档隐性关联。"文档 A 说系统 X 依赖 Y、文档 B 说 Y 已废弃"——字面上没有重合，但图里 X—Y 一查就通。
  - 代价：建图成本高、延迟大，只对高频核心知识建图，不做全量。
- **面试加分词**："向量找相似文本，图谱找关联关系——多跳推理、全局性问题用 GraphRAG。"

### 15. Ragas 评估与 RAG 指标

- **一句话定义**：评估 RAG 系统好坏的四个量化指标。
- **扩展**：
  - **Faithfulness 忠实度**：回答能否在检索片段里找到依据（防幻觉，最关键）。
  - **Answer Relevance 答案相关性**：回答和问题对不对得上。
  - **Context Relevance 上下文相关性**：检索出来的片段本身和问题相关（召回质量）。
  - **Context Recall 覆盖率**：问题所需信息有多大比例被检索出来。
- **面试加分词**："四个指标分别对应防幻觉、防跑题、查检索、查召回——先量化，再调优。"

### 16. Agent / ReAct / LangGraph / MCP

- **一句话定义**：让大模型具备"思考 + 行动 + 观察"循环能力的框架体系。
- **扩展**：
  - **ReAct**：模型输出"思考（Reason）→ 行动（Act：工具+参数）→ 观察（Observe 工具结果）"，再回到思考，直到给答案——"想一步做一步"。
  - **LangGraph vs LangChain**：LangChain 的 LCEL 是**线性链**，"一链走到底"；LangGraph 是**状态机（图）**：节点、边、共享 State，支持循环、分支、持久化——多 Agent 协同必选它。
  - **MCP（模型上下文协议）**：统一模型与外部工具/数据的接入标准（工具注册、资源、提示模板），模型不用为每家工具单独写集成。
  - **工具调用（tool calling）**：模型输出结构化工具+参数，框架执行后回传结果——ReAct 循环里的"行动"环节。
- **把项目串进去**：我的 OmniAgent 用 LangGraph，节点=意图识别→工具路由（Supervisor）→ 检索/SQL/Code Worker→合并→生成；MCP 标准化接入工具。

### 17. vLLM 与高性能推理

- **一句话定义**：高吞吐 LLM 推理服务框架，核心是 PagedAttention 与连续批处理。
- **扩展**：
  - **PagedAttention**：把 KV Cache 按固定大小的最近分页管理，像操作系统的内存分页——避免显存碎片、几乎零浪费，支持共享 KV Cache（并行采样）。
  - **连续批处理（continuous batching）**：批内请求动态进出——不等整批完成，完成的先走、新来的补位，GPU 不空转。
  - 对外暴露 **OpenAI 兼容协议**（/v1/chat/completions），各家模型统一接口接入。
- **面试加分词**："遇到显存碎片、吞吐低时，选 vLLM 这类做连续批处理和 KV 缓存分页的框架。"

### 18. 熔断 / 降级 / 限流（网关三件套）

- **熔断**：三态 CLOSED→OPEN→HALF_OPEN，失败次数超阈值切断请求快速失败，冷却后试探放行。
- **降级/故障转移**：按优先级候选模型列表，主不可用自动切备（如补充提示词兜底文案）。
- **限流**：令牌桶（按速率取令牌，支持突发） /滑动窗口（固定窗口值更平滑），按 API Key 维度。
- **一句话记忆**：**熔断防雪崩、降级保可用、限流护后端——三件套一道用。**

### 19. JWT 认证

- **一句话定义**：无状态 token 认证，Token 三段式 header.payload.signature，服务器只验签不存会话。
- **扩展**：签名防篡改、无状态、易水平扩展；缺点是无法主动吊销 → 可为主 JWT 短时效+refresh token。
- **常见追问**："无状态怎么续期？"→ 短 access token + 长 refresh token；"怎么撤销？"→ 黑名单/版本号。

### 20. Pipeline 与工程化知识

- **Docker**：镜像分层 + 容器隔离（共享宿主内核）；Docker Compose 一键编排多服务。
- **Alembic**：数据库迁移工具，schema 变更版本化（upgrade head / revision）。
- **CI/CD + GHCR**：push 自动构建镜像 → 推到 GitHub Container Registry → 服务拉取部署。

- **JWT**：见上条。
- **速率限制**：令牌桶/滑动窗口。

### 21. PostgreSQL / pgvector / Neo4j / 向量库选型

- **pgvector**：PG 的向量扩展，把 PG 变成一个"最熟悉的 SQL + 向量检索"——RAG 最常用。
- **Neo4j**：图数据库，知识图谱的载体（GraphRAG 落地）。
- **FAISS / ChromaDB / Qdrant**：FAISS 是算法库（非数据库）；ChromaDB 适本本地开发；Qdrant 为生产级、支持高级过滤/超大规模。
- **面试一句**："我熟悉 PG + pgvector，向量入库、向量检索一体，其他库了解深浅。"

**pgvector 是插件,不是独立数据库**(面试高频抠细节):
- 本质:PG 的**扩展模块**,没有独立进程/服务器/存储,数据存在 PG 库里,查询用 PG 的 SQL。
- 类比:pgvector 是手机的"测距 App"、Chrome 的"翻译插件";Qdrant/Milvus 是"另一台独立机器"(自己的服务器+存储)。
- 对比:pgvector=简单、业务数据+向量一起管;Qdrant/Milvus=超大规模、性能极致、要多维护一套系统。

**为什么用 PG 做 AI 应用(选型回答)**:
1. 功能全:复杂查询/窗口函数/JSON/全文搜索原生支持;
2. pgvector 插件一装,向量检索与业务数据同库;
3. 约束严格、数据一致性更强;
4. 开源社区活跃,AI 新玩法先支持 PG。

**pgvector 用法(RAG 召回一步到位)**:
```sql
CREATE EXTENSION vector;
CREATE TABLE documents (
    id SERIAL PRIMARY KEY,
    content TEXT,
    embedding vector(1024)      -- 向量列
);
-- 相似检索:<=> 余弦距离,取最像 5 条
SELECT id, content FROM documents
ORDER BY embedding <=> '[...]' LIMIT 5;
-- 先过滤再检索(一条 SQL 合体):
SELECT id, content FROM documents
WHERE user_id = 4
ORDER BY embedding <=> '[...]' LIMIT 5;
```

**向量库选型判断逻辑**:小项目+业务数据一起查 → pgvector;超大规模独立扩展 → Qdrant/Milvus;知识图谱/图关系 → Neo4j;纯本地原型 → ChromaDB;纯算法研究 → FAISS。

**面试一句话（背）**："pgvector 是 PG 的向量扩展插件,不是独立数据库——数据存 PG 库、SQL 照常用,好处是向量检索和业务数据同库,一条 SQL 同时过滤+检索;超大规模才需要换独立的专业向量库(Qdrant/Milvus)。选型:小项目 pgvector,大规模 Qdrant,图场景 Neo4j。"

### 22. 流式补充：TTFT / Token 管理

- **TTFT（首 token 延迟）**：从请求发出到收到第一个 token 的时间，最影响体感——模型件流式优化、网关透传（边收边发不累积）。
- **Token 管理**：无 tokenizer 的启发式估算（中英混合加权），动态限制 max_tokens 防超出上下文窗口。
- 一句话：**首 token 损失体感，token 管理保上限**。

### Python：global 与 nonlocal 区别

| | global | nonlocal |
|---|---|---|
| 作用对象 | 模块级全局变量 | 嵌套函数的外层局部变量（闭包） |
| 位置 | 任意函数内 | 仅在嵌套函数内 |
| 效果 | 改 = 改全局 | 改 = 改外层局部 |

**一句话**：函数内修改全局变量用 `global`；修改外层函数的局部变量用 `nonlocal`。

### Python：如何实现一个单例（高频，务必会）

补上一个过想要的实现即可，讲原理：

```python
class Singleton:
    _instance = None
    def __new__(cls, *args, **kwargs):
        if cls._instance is None:
            cls._instance = super().__new__(cls)
        return cls._instance
```

**加分**：单例的三种实现方式对比（`__new__` / 装饰器 / 模块），突出"模块天然是单例"。并说明使用时机：连接池、配置对象等全局唯一场景。

### Python：协程 / 线程 / 进程 的区别（关联 GIL）

| | 进程 | 线程 | 协程 |
|---|---|---|---|
| 调度单位 | 进程（内核调度） | 线程（内核调度） | 协程（用户态，事件循环） |
| 资源开销 | 大（独立地址空间） | 中（同进程共享内存） | 小（单线程内切换） |
| GIL 影响 | 无（each process 多核） | 有（同进程 CPU 密集受限） | 无（IO 等待时让出） |
| 适用场景 | CPU 密集 | IO 密集（较轻） | 高并发 IO（网络请求、流式） |

**一句话**：CPU 密集用多进程；IO 密集用多线程或协程；网关/流式场景用协程。

### Python：列表推导式 与 生成器表达式 的区别

```

### 情况1: 在哪里出来（最重要的记忆点）
- 列表推导式用 `[]`（list），一次性生成**全部元素**，占用内存。
- 生成器表达式用 `()`（**不是元组**，这是个高频陷阱），**惰性求值**，一次只产一个元素，省内存。
```

## A. 语言基础

### 1. Python 是解释型还是编译型？
边解释边执行（CPython 先编译成字节码 .pyc 再解释到虚拟机）。特点：跨平台、开发快、慢于编译型。

### 2. 不可变对象 vs 可变对象 ★
- 不可变：int / str / tuple / frozenset —— 内容不可改，改即换对象（id 变）。
- 可变：list / dict / set —— 内容可改（id 不变）。
- 要点：**函数传参，可变对象修改影响外部** → 面试常问"为什么内部改了外面也变了"。避免方法：传副本或返回新对象。

### 3. is 与 ＝＝（双等号）的区别 ★
- 双等号（==）比较**值**；`is` 比较**身份（id）**。
- 陷阱：小整数缓存（-5~256）与短字符串可能 id 相同，但大对象一定不同。
- 背诵：**判空用 `if x is None`，比较值用双等号（==）**。

### 4. 深拷贝 vs 浅拷贝 ★

**概念**:
- `copy()`（浅）：拷贝外壳，内部元素仍是引用 → 改内部会被波及。
- `deepcopy()`（深)：递归拷贝全部层级 → 完全独立。
- 高频考点：**浅拷贝改嵌套 list 会影响原列表；深拷贝不会**。

**面试完整版答法（直接背）**：
> "浅拷贝用 `copy.copy()`，相当于新做了一个外壳，但外壳里嵌套的对象还是原来那些引用——所以我在新外壳里往里加元素，原列表不受影响；但一旦我修改内部的嵌套 list，原列表就会跟着变，因为它们共享同一份内部对象。深拷贝用 `copy.deepcopy()`，里外全复制成独立的新对象，两边互不干预；代价是内存开销大。所以浅拷贝省内存、速度快，适合只改外壳的场景；深拷贝彻底独立，适合需要数据隔离的场景。"

**实际项目场景（数据清洗场景必用）**：
> "我做数据处理时，拿到的是嵌套的 JSON/Excel 列表（比如一条记录里嵌着子表、指标数组）。清洗过程中要**保留原始数据做对比和回溯**，又要生成多版处理结果——这时候直接对原始结构动手会把原数据污染掉，所以对原始数据做 `deepcopy()` 存一份只读基线，后面过滤、去重、补缺都操作副本；而只对最外层做整体替换（比如按某列排序后重新组装）时用浅拷贝就够了，省内存、速度快。"

**一句话记忆**：深拷贝 = 留"原始数据底稿"，浅拷贝 = 只换"外面的包装"。

**面试被追问"你项目里用过吗"——举例模板（口述版，背熟）**：
> "用过，最典型的是在**清洗 Excel/CSV 导入的数据**时。数据是一行一条记录，有些字段里嵌着列表（比如一个客户的多个联系记录）。
> 我处理的时候**先 Deepcopy 一份原始数据存着当底稿**——因为要反复对比清洗前后的差异、也要回溯原始值；然后在副本上做去重、补缺值、格式转换这些操作，原始那份永远不动。
> 浅拷贝也用——比如只按某个字段重新排序组装最外层时，用浅拷贝，快、省内存，因为不动嵌套内容。"

**追问接招表（背下来防穿帮）**：

| 面试官问 | 你答 |
|---|---|
| "具体 copy 的什么?" | "一张客户数据表，一行一个客户，客户有个字段装他名下的多个订单/记录（list）" |
| "为什么不全改原数据?" | "要对比清洗前后、要回滚，原数据是基线，污染了就找不回原始版本" |
| "浅拷贝什么时候用?" | "只重组最外层、不动嵌套内容时的排序、筛选场景，开销小" |
| "那 pandas 的话呢?" | "其实 pandas 里 `.copy()` 默认也是浅拷贝，处理 DataFrame 子集时也怕改到源数据" |

**最后一句点睛（显真功底）**：因为你是数据分析出身，主动补一句 pandas 的 `.copy()` 陷阱，面试官会瞬间觉得你是真写过代码的人，而不是背答案。

**兜底话术（细节模糊时用）**：

### 5. 什么是 GIL？影响与解决 ★
- GIL：CPython 的全局解释器锁，同一时刻只允许一个线程执行字节码。
- 影响：**多线程无法提升 CPU 密集任务的性能**；IO 密集不受影响。
- 解决：`multiprocessing`（多进程，ProcessPoolExecutor）或协程；极端 CPU 密集场景也可考虑不受 GIL 影响的 PyPy 或 C 扩展。

### 6. 占位参数 *args / **kwargs（注意：** 是参数语法，不是加粗）
- `*args`：收集多余位置参数为元组；`**kwargs`：收集关键字参数为字典。
- 也用于解包：`func(*list)`、`func(**dict)`、`a, *rest = items`。

**读法**：`*args` 读"星 args"，`**kwargs` 读"双星 kwargs"（args=位置参数，kwargs=关键字参数）。

**核心心法（一个星号两种活法）**：
- 定义时用 `*` = **收集（打包）**：`def f(*args)` → `f(1,2,3)` 则 args=(1,2,3) 元组；`def f(**kw)` → `f(a=1)` 则 kw={'a':1} 字典（键=参数名，值=传的值）。
- 调用时用 `*` = **解包（拆开）**：容器拆成一个个按位置/关键字喂进函数。

**全部场景表（背）**：

| 写法 | 作用 | 例子 |
|---|---|---|
| `def f(*args)` | 收多余位置参数为元组 | `f(1,2,3)` → args=(1,2,3) |
| `def f(**kwargs)` | 收多余关键字参数为字典 | `f(a=1)` → kwargs={'a':1} |
| `f(*lst)` | 调用时列表拆开按位置传 | `f(*[1,2,3])` 等价 `f(1,2,3)` |
| `f(**dic)` | 调用时字典拆开按关键字传（键名须与参数名一致） | `f(**{'a':1})` 等价 `f(a=1)` |
| `a, *rest = items` | 赋值解包，rest 收"剩下的"（永远是列表） | `a,*r=[1,2,3]` → a=1, r=[2,3] |
| `[*a, *b]` | 列表任意位置拼接 | `[0, *a, 6]` |
| `{**a, **b}` | 字典合并，**后面覆盖前面** | `{**d1, **d2}` |
| `{**defaults, **override}` | 默认配置被用户参数覆盖（实战常用） | 只改 port 其余保留 |
| `print(*lst)` | 展开成多个参数 | `print(*[1,2])` → `1 2` |
| `zip(*matrix)` | 矩阵转置/解包配对 | `keys, vals = zip(*pairs)` |
| `_, *rest` | 下划线变量=不管/忽略 | `_, *rest = items` |

**实战场景**：装饰器里 `def wrapper(*args, **kwargs)` 收进来再原样 `func(*args, **kwargs)` 转发；`{**DEFAULTS, **override}` 拼接口/模型参数（默认配置 + 用户覆盖）。

### 7. 什么是闭包（closure）★
- 内嵌函数引用外层函数的局部变量，并随返回的函数带到外部使用 → 变局部变量"存活"于函数外。
- 经典例子：计数器。注意用 `nonlocal` 才能改外层变量。

**完整理解（面试回答骨架）**：
> "闭包 = 内层函数 + 它'记住'的外层函数局部变量。外层函数把内层函数返回出去时，内层函数连同外层局部变量一起被带走，即使外层函数已结束，这些变量依然活着。用 `nonlocal` 才能修改外层变量（对应 `global` 管模块级）。"

**计数器手写题（必背）**：
```python
def make_counter():
    count = 0
    def tick():
        nonlocal count   # ★ 不加会报 UnboundLocalError
        count += 1
        return count
    return tick

c = make_counter()   # c 拿到的是函数 tick（此刻 tick 还没执行！）
print(c())  # 1   ← print 打印的是 c() 的"返回值"
print(c())  # 2
print(c())  # 3
```
关键理解：**定义函数 ≠ 执行函数**。`make_counter()` 只创建函数并返回；`c()` 才真正执行 tick 内部。闭包让 count 每次调用都记住上一次的值（同一份 count）。

**循环闭包陷阱（面试坑，必讲）**：
```python
funcs = []
for i in range(3):
    funcs.append(lambda: i)        # 未修复
print([f() for f in funcs])       # [2, 2, 2] 不是 [0,1,2]！
```
**原因**：`lambda: i` 的函数体是"调用时再看 i"，闭住的是**变量 i（地址）不是值**（快照）；循环结束后 i 停在最终值 2，所有函数再读都是 2。
**修复**：`lambda i=i: i`（默认参数在创建那一刻求值并固定，焊死当时的 0/1/2）→ 输出 [0,1,2]。

**为什么默认参数能锁值？——求值时机的两条铁律（必背）**：
1. **函数体是延迟执行**的：定义时只存代码，调用时才去看 i 是多少 → `lambda: i` 结果随时间变。
2. **默认参数定义时立刻求值一次**：`lambda i=i: i` 中参数列表的 `i=` 右侧在函数创建瞬间求值并固定 → 拍照定格。
- 类比：`lambda: i` 是便利贴"下楼看钟几点了"（活的）；`lambda i=i: i` 是"下午3点整"（死快照）。
- 同源坑：可变默认参数 `def f(lst=[])` 只创建一次列表，多次调用共享 → [1], [1,2]。

### 8. 什么是装饰器？★
- 不修改原函数代码，用 `@` 给函数添加额外行为（日志、计时、鉴权、缓存）。
- 手写模板：

```python
def my_decorator(func):
    @functools.wraps(func)      # 保留原函数名/文档
    def wrapper(*args, **kwargs):
        result = func(*args, **kwargs)   # 执行前/后可插逻辑
        return result
    return wrapper
```

### 9. yield 与生成器是什么？★
- 生成器：一边生成一边返回，用 `yield` 写法；不一次性存全部，省内存。
- 与 `return` 区别：`yield` 暂停、保存状态（下次从这继续）；`return` 结束。
- 应用：大文件逐行读、流式处理、无限序列。

**大文件逐行读的底层原理（面试讲这个亮眼）**：
- **"打开"≠"加载"**：`open()` 只是向操作系统申请文件句柄，此时一个字节都没进内存；真正读入发生在循环取行时。
- **文件对象本身就是惰性迭代器**：`for line in f` 内部按缓冲块（约 8KB）从磁盘拉取，内存里永远只装"一块缓冲 + 当前一行"，不是全文件装进内存。
- **yield 在惰性之上再加控制层**：每次 `next(gen)` 才推进一行（可先做 strip/转换/过滤），不需要时完全不动磁盘。
- 对比警醒：`readlines()` / `read()` 才会一次性全加载，大文件会爆内存。

```python
def read_lines(path):
    with open(path, encoding="utf-8") as f:   # 只打开句柄,没读
        for line in f:                        # 按 8KB 缓冲块逐行喂
            yield line.strip()                # 要一行才推进一行
```

- 面试一句话："open() 只建句柄；文件对象是惰性迭代器，for line in f 按缓冲块逐行读取；yield 再包一层逐行清洗，内存恒定为一行+缓冲。readlines()/read() 才会全量加载。"

### 10. 迭代器（Iterator）与迭代对象（Iterable）
- Iterable：可 for 循环的对象（list/str/dict/generator）。
- Iterator：`next()` 一个一个取，`__iter__` 返回自己，`__next__` 返回下一个，耗尽抛 StopIteration。
- 生成器是天然的迭代器。

### 11. __init__ 与 __new__ 的区别 ★
- `__new__`：**创建对象**（类方法，先执行）；`__init__`：**初始化**（后执行）。
- 单例：在 `__new__` 里判断并复用实例（见九章）。

**补充 1：普通类不写 __new__ 时谁创建实例？**
- 沿继承链向上找，最终调用 `object.__new__(cls)` 创建空壳，再执行 `__init__` 填属性。
- 验证：`Person.__new__ is object.__new__` → True（没重写就是祖传的）。
- super().__new__(cls) = 借父类（object）的默认创建动作，自己不发明创建姿势。

**补充 2：如何理解"单例模式"（概念层）**
- 单例 = 一个类全局只允许一个实例，常用于连接池、配置、日志、缓存（贵或全局唯一的资源）。
- 核心逻辑："第一次创建并缓存，之后直接返回缓存"。
- 拦截点必须在 `__new__`（创建之前），`__init__` 管不到"唯一性"。

**单例完整代码（背）**：
```python
class Database:
    _instance = None
    _initialized = False          # 标志位：贵的初始化只做一次

    def __new__(cls):
        if cls._instance is None:
            cls._instance = super().__new__(cls)   # 第一次创建并存
        return cls._instance      # 之后每次直接返回旧实例

    def __init__(self):
        if not Database._initialized:
            print("真正建立连接")      # 昂贵动作
            Database._initialized = True
        # 否则什么都不干，复用
```
- db1 = Database() 第二次 db2 = Database() → db1 is db2 → True。
- 每次 `Database()` 都会执行 `__init__`（哪怕拿的是旧实例），所以昂贵初始化要加标志位只做一次。

**单例的其他两种写法（面试扩展）**：
1. **装饰器版**：闭包缓存 `instances = {}`，把类包装成"只创建一次的函数"（不改类内部）。
```python
def singleton(cls):
    instances = {}
    def get_instance(*args, **kwargs):
        if cls not in instances:
            instances[cls] = cls(*args, **kwargs)
        return instances[cls]
    return get_instance

@singleton
class Database:
    pass
```
2. **模块天然单例**：`db.py` 模块级 `db = Database()`，其他地方 `from db import db` —— Python 模块只加载一次，自带单例效果（社区推荐）。

**面试一句话（背）**："单例 = 一个类全局只有一个实例。实现方式：`__new__` 拦截（第一次创建缓存、之后复用）、装饰器包装、或模块级天然单例。昂贵初始化要加 `_initialized` 标志位防止重复执行。"

### 12. 类方法 / 静态方法 / 实例方法
- 实例方法：第一个参数 self。
- `@classmethod`（第一个参数 cls）→ 可访问类属性，常作工厂方法。
- `@staticmethod` → 不接 self/cls，当作独立函数放在类里。区别考点：classmethod 可被子类复用逻辑。

**核心心法（为什么有三种）**：方法存在的意义是访问"数据"，数据分三层存放 → 需要哪层数据就用哪种方法：
- 实例方法 = 操作**单个实例**的属性（self.name 这种）→ 日常 90% 场景
- 类方法 = 操作**类本身**的数据/当工厂创建实例 → cls
- 静态方法 = 纯工具函数，不需要任何实例/类数据 → 无参数自动传入

**调用时 Python 自动塞第一参数（最容易卡的点）**：

| 你写 | Python 内部实际执行 | 自动传参 |
|---|---|---|
| `u.spend(30)` | `spend(u, 30)` | self = u（实例） |
| `User.from_json(payload)` | `from_json(User, payload)` | cls = User（类） |
| `Order.calc_total([1,2])` | `calc_total([1,2])` | 无 |

**类方法=工厂方法（逐行理解）**：
```python
class User:
    def __init__(self, name, age):     # 构造实例
        self.name = name
        self.age = age

    @classmethod
    def from_json(cls, data):          # cls 自动 = User 类本身!
        return cls(data["name"],       # cls(...) = User(...) = 创建新实例
                   data["age"])

payload = {"name": "小红", "age": 20}
u = User.from_json(payload)            # 不用传 cls!自动塞入 User
```
- `cls(...)` = 调这个类自己的构造 → 工厂流水线:给原材料(dict/JSON/db行),产出成品实例
- **子类复用**:`Admin.from_json(...)` 自动塞 Admin → 造出 Admin 实例。静态方法写死 User 就永远是父类 → 工厂必须用 classmethod

**静态方法=类里的纯工具（逐行理解）**：
```python
class Order:
    @staticmethod
    def calc_total(prices):            # 没有 self/cls!直接是真正参数
        return sum(prices)             # 纯计算

    def final_price(self, tax_rate):   # 实例方法
        total = Order.calc_total(self.items)   # 用类名调用静态方法
        return total * (1 + tax_rate)
```
- 调用姿势：`Order.calc_total([10,20,30])`（类名调，常用）/ 实例调也行
- 无自动传参 → prices 就是第一个参数
- "静态"= 不掺杂任何实例/类状态，放类里只为归类（如"订单计算放 Order 类"）

**真实场景（面试关联）**：Pydantic 的 `model_validate()`、SQLAlchemy 的 sessionmaker 都是类方法（工厂）——FastAPI 里天天间接在用。

**三大陷阱（面试拉分点）**：
1. classmethod vs staticmethod 继承差异：classmethod 用 cls 造子类实例，staticmethod 写死父类
2. `staticmethod` 里要用类属性得写 `User.count`（没有 cls）
3. 实例上也能调类方法/静态方法，但规范是类名直接调

**面试一句话（背）**："三种方法设计是为了访问正确的数据层：实例方法操作单实例属性；类方法收 cls 当工厂创建实例（子类自动用子类，如 Pydantic model_validate）；静态方法是纯工具函数。选择标准：方法需要哪层数据就用哪种。"

### 13. 类变量 vs 实例变量
- 类变量（class variable）：声明在类体，**所有实例共享同一份**；有人修改会影响所有实例。
- 实例属性（self.x）：属于单个实例，各改各的。
- **最大的坑：可变类变量会被所有实例共享**：
```python
class Cart:
    items = []          # ❌ 类变量！所有购物车共用一个列表

cart1 = Cart(); cart2 = Cart()
cart1.items.append("苹果")
print(cart2.items)      # ['苹果'] ← cart2 凭空多出一个苹果！
```
修复：把默认数据放进 `__init__` 里 `self.items = []`（每个实例一份）。
- 类变量适合放：常量/全局配置（如 `MAX_RETRY = 100`）、跨实例计数器（`cls.count += 1`）。
- **面试一句话（背）**："类变量定义在类体、所有实例共享；实例变量属于单个实例。坑：可变类型默认放在类体（如 `items = []`）会导致所有实例共用同一个列表，应该放 `__init__` 里用 `self.items = []`。"

### 14. Python 内存管理 & 垃圾回收 ★
- **引用计数为主**：每个对象记录"被引用的次数"，归零立即回收。
  - `a = obj` 计数 +1；`a` 被覆盖/`del a` 计数 -1。
  - `sys.getrefcount(obj)` 返回值比真实计数多 1（它自己也算一次引用）。
- **循环引用兜底用分代 GC**：A 引用 B、B 引用 A，双方计数永远不为 0 → 靠分代标记-清除定期回收；`gc.collect()` 可手动触发。
- **常见内存泄漏**（背三条）：
  1. 无界缓存/全局 list 一直 append 不清
  2. 大对象 + 循环引用滞留（分代 GC 有延迟）
  3. 闭包长期持有大对象（生成器没跑完 = 闭包挂着外部大数据结构）
- **面试一句话（背）**："Python 内存管理以引用计数为主，计数归零立即回收；循环引用靠分代 GC 标记-清除兜底。防泄漏：不用无界缓存、闭包不长期 hold 大对象、大文件用 with 及时释放句柄。"

### 15. try / except / else / finally 的执行顺序
- **顺序表（背熟）**：

| 情况 | 执行顺序 |
|---|---|
| try 没有异常 | try → else → finally |
| try 抛异常且 except 捕获 | try → except → finally |
| try 抛异常无 except 匹配 | 异常向上抛，finally 依然执行 |

- **finally 永远执行**（就算 return 也会先走 finally）；**else 只在没异常时执行**（放"成功后的事"）。
- 细节（面试点）：
  - except 从上到下匹配，**多子类在前**（`except ValueError` 要在 `except Exception` 前），最后可用 `except Exception` 兜底。
  - `except (TypeError, ValueError):` 一次性捕获多种。
  - `finally` 不要写 return：会覆盖 try 里的返回值。
  - 裸 `except:` 会连 `KeyboardInterrupt` 都吞掉，生产不用。

**return 与 finally 的执行机制（面试手写题必考）**：
- 真实轨迹：执行到 `return 1` → 先把 1 **暂存起来** → Python 强制先过 finally 关 → finally 跑完没有 return → 把暂存的 1 交出去，函数才真正结束。
- **如果 finally 里也写了 return → 它重新暂存新值，把 try 里暂存的值顶掉 → 最终返回 finally 的值**：
```python
def f():
    try:
        return 1     # ① 暂存 1
    finally:
        return 3     # ② 重新暂存 3，顶掉 1 —— 最终返回 3！
```
- 类比：机场安检——return 是登机口，finally 是安检门，**凡是离开的人必经这道门**；安检员若改你目的地，最终去的就是安检说的地。连异常向外抛也要先过 finally（所以资源清理放 finally 永远靠谱）。
- 规范：**finally 里绝不写 return**。
- 代码习惯：**资源释放放 finally**（或直接 with），隐藏业务放 finally。
- **面试一句话（背）**："try 放可能出错的代码，except 对应捕获（顺序匹配、子类在前），没异常时执行 else，finally 无论如何都执行——所以资源清理放 finally。注意 finally 里不要 return，会覆盖 try 的返回值。日常用 with 代替 try/finally 管理文件。"
- `else`：无异常时执行；`finally`：无论异常与否，都执行（常用关资源）。
- 异常链：`raise ... from ...`；自定义异常继承 Exception。

### 16. 上下文管理器 with
- 效果：自动 `__enter__` / `__exit__`，保证资源释放（文件、锁、连接）。
- 高频用法：`with open(...) as f`、`with aq.get_lock():`（FastAPI/SQLite）、自己写用 `contextmanager`。

**为什么需要 with**：文件/连接/锁不用完必须还回去。直接 `f.close()` 一旦中途报错就执行不到 → 泄漏。`with` = try/finally 的语法糖，自动关闭，人不可能忘。

**原理（类比：酒店入住退房）**：
- `__enter__`：进入时调用（入住登记），返回值给 `as` 后面的变量（房卡）。
- `__exit__`：退出时**必调用**（退房结算），正常退出/异常退出都会执行 → 释放资源放这里。
- 执行轨迹：`with open(...) as f:` → ① open 得到对象 → ② `__enter__` → ③ 块内代码 → ④ 无论如何走 `__exit__` 关文件。

**自己写上下文管理器（两种方案）**：
```python
# 方案 A：@contextmanager（推荐）
from contextlib import contextmanager

@contextmanager
def auto_close():
    print("打开资源")        # yield 前 = __enter__
    try:
        yield "连接对象"      # yield 把值交给 as 变量
    finally:
        print("关闭资源")     # yield 后 = __exit__，必执行

# 方案 B：手写类
class MyConn:
    def __enter__(self):
        print("打开"); return self
    def __exit__(self, exc_type, exc_val, exc_tb):
        print("关闭")
        # return False → 异常继续上抛；return True → 吞掉异常
```

**面试一句话（背）**："with 是上下文管理器，自动调用 `__enter__`（进入时返回资源）和 `__exit__`（退出时必释放），等价于 try/finally 语法糖。自己写推荐 `@contextmanager`，yield 前是打开、yield 后是关闭。"

### 17. 列表 / 元组 / 集合 / 字典 的适用场景 ★
- list：有序可重复，读 O(n)。-- 默认容器，遍历/排序/栈队列
- tuple：不可变，可哈希可作 dict 键。-- 固定记录、函数返回多值、dict key
- set：去重、交集/并集 O(1) 查找。-- 去重、成员判断
- dict：键值映射 O(1) 查值；Python 3.7+ 保插入顺序。
- 提问：**一个列表去重** → `list(set(l))` 但不保序；保序用 `dict.fromkeys(l)`。
- 成员判断性能：`x in set` O(1) vs `x in list` O(n) —— 频繁判断用 set。

**`dict.fromkeys(l)` 逐步拆解（为什么能去重+保序）**：
```python
l = [3, 1, 3, 2, 1]
dict.fromkeys(l)   # {3: None, 1: None, 2: None}
list(dict.fromkeys(l))   # [3, 1, 2]
```
- `fromkeys` 是**类方法（工厂）**：把列表每个元素当 key、value 统一塞 None 建新字典。
- 去重靠：**key 不能重复**，同 key 第二次出现直接覆盖，挤不进来。
- 保序靠：**py3.7+ 字典保插入顺序** → 留下的顺序 = 原列表首次出现顺序（不是排序！）。
- 三选一口诀：`set(l)` 乱序 / `dict.fromkeys(l)` 保首次顺序 / `sorted(set(l))` 才是真排序。

**`list(字典)` 为什么只拿 key**：Python 字典的**迭代协议默认按 key 遍历**，`list(d)` = `[k for k in d]`。拿 value 用 `list(d.values())`，拿键值对用 `list(d.items())`。

**为什么 dict 的 key 要可哈希**：查找先算 hash，内容变了 hash 对不上就找不到了。tuple 不可变 → hash 稳定 ✓；list 可变 → hash 会变 → 被禁止。
- `return x, y` 本质是返回 tuple（配合解包 `a, b = f()`）。

**面试一句话（背）**："list 有序可重复是默认容器；tuple 不可变可哈希作 dict key；set 去重 O(1) 成员判断；dict 键值 O(1) 保序。去重保序 `dict.fromkeys(l)`；key 必须可哈希所以 tuple 可以、list 不行。"

### 18. sorted / sort / reverse / lambda + key 考点
`sorted(iterable, key=..., reverse=True)`；`sort()` 只在列表。`key` 常配合 `lambda x: x[1]`。

**sorted vs sort 根本区别**：
| | `list.sort()` | `sorted(...)` |
|---|---|---|
| 谁的方法 | 只有 list | 内置函数，任何可迭代对象 |
| 原数据 | **原地修改** | **返回新列表**，原数据不动 |
| 返回值 | **None** | 排序后新列表 |

- 高频坑：`l = l.sort()` → sort 返回 None，列表变 None！要 `l = sorted(l)` 或直接用 `l.sort()` 不接返回值。
- `reverse=True` 整体倒序（是"排完再倒"，不是"按反转排"）。

**key 参数（核心）**：决定"按什么比大小"——每个元素过一遍 key 函数，用结果比较，原元素不变。
```python
sorted(words, key=len)                    # 按长度排
sorted(scores, key=lambda x: scores[x])   # dict 默认迭代拿 key，按 value 排
sorted(scores.items(), key=lambda item: item[1])  # 排好序的 (k,v) 对
```
- **多级排序**：key 返回元组，先比第一位同再比第二位：`key=lambda s: (s[1], -s[2])`（负号实现单列降序）。

**lambda 一句话**：`lambda 参数: 表达式` 匿名单表达式函数，常用作 key；def 可写多行逻辑且可复用。

**面试一句话（背）**："`sort()` 列表专属、原地排序、返回 None；`sorted()` 内置函数、任意可迭代、返回新列表。key 决定比较依据（如 `key=len`、`lambda x: x[1]`），返回元组可多级排序；reverse=True 整体倒序。"

### 19. HTTP API 相关：状态码必背
- 2xx 成功；4xx 客户端错（404 不存在 / 400 参数错 / 401 未认证 / 403 无权限 / 429 限流）；5xx 服务端错（500）。
- 提问常考：**如果别人调你的接口拿不到数据，先看是 404 还是 500 → 排查思路**。

**五类状态码（看百位数字）**：1xx 信息 / 2xx 成功 / 3xx 重定向 / 4xx 客户端错 / 5xx 服务端错。

**必背清单**：
- 200 成功；201 创建成功（POST 后）；204 无内容（DELETE 成功常用）
- 301 永久重定向 / 302 临时重定向
- 400 请求格式错（参数缺/类型错）→ 客户端锅
- **401 未认证**（没登录/没带 token）vs **403 无权限**（认证了但不配）→ 401"你谁啊"，403"你不行"
- **400 请求本身有问题 vs 404 资源不存在**（URL 错/数据没了）
- 405 方法不允许（GET 调只准 POST 的接口）
- 429 限流触发；500 代码崩了（服务器锅）；502/503/504 网关与超时（微服务高频）

### 20. REST 基础：GET/POST/PUT/DELETE + 幂等性
- GET 查 / POST 新增（默认非幂等）/ PUT 全量更新（幂等）/ DELETE 删除。
- 口 API 设计：**统一返回 JSON {code, msg, data}**，错误有明确 message。

**GET vs POST 对比表**：
| | GET | POST |
|---|---|---|
| 用途 | 取数据 | 提交/创建 |
| 参数 | URL 查询串 `?a=1` | body |
| 幂等 | **幂等**（N 次结果相同） | **不幂等**（每次新增一条） |
| 缓存 | 可缓存 | 不缓存 |
| 安全 | 参数暴露在 URL/日志 | 相对隐蔽 |

- 防重复提交 → 幂等键（Idempotency-Key）或唯一 ID。
- PUT 整体替换（幂等）、PATCH 部分更新（不幂等）、DELETE 删除（幂等）。

**REST 一句话定义（背）**："把一切抽象成资源，URL 只放名词（资源），HTTP 方法表达动词（操作），状态码表达结果。GET /users/1 读用户、POST /users 创建。好处：语义清晰、无状态、可缓存、前后端解耦。"
- 铁律：URL 用名词复数、层级用 `/`（从属关系 `/articles/1/comments`）、返回 JSON、响应带正确状态码。
- 反例：`GET /get_user`、`POST /delete_user`——URL 里塞动词，不是 RESTful。
- 情景题答案：GET/POST /articles、PUT/DELETE /articles/1、GET/POST /articles/1/comments、DELETE /comments/5。

### 21. 数据库手写题：索引、事务、范式
- 索引：加速 WHERE/JOIN/ORDER BY 查询，代价是写慢 + 占用空间。**不要滥用**；联合索引遵循最左前缀。
- 事务：ACID（原子性、一致性、隔离性、持久性）。
- 隔离级别：读未提交＜读已提交（PG 默认）＜ 可重复读＜串行化。
- 面试口头常问：**GET 为什么会变慢？** → 检查是否缺索引 / 全表扫 / N+1。

### 22. N+1 查询问题（AI 项目高频）★
- 遍历主表逐条查子表 → N 次额外查询。
- 解决：SQLAlchemy `joinedload` / `selectinload` 预加载；或一次性 `IN` 查。

**N+1 是什么**：1 次主查询 + N 次子查询(N = 主查询行数)。查 100 个用户的订单 = 1 + 100 = 101 次查询(每次都是网络往返),比 2 次查询慢几十倍。
```python
# ❌ N+1:循环里查库
users = db.query(User).all()
for user in users:
    db.query(Order).filter_by(user_id=user.id).all()   # 100 次查询!

# ✅ 方案一:ORM 预加载(1~2 次查询)
users = db.query(User).options(joinedload(User.orders)).all()
# 或 selectinload(User.orders) —— 两条 SQL,不会 N 条

# ✅ 方案二:手动 IN(裸 SQL 场景)
user_ids = [u.id for u in users]
orders = db.query(Order).filter(Order.user_id.in_(user_ids)).all()  # 1 次 IN
```
- **识别信号**:循环里有数据库查询 = N+1 的味道;接口变慢排查时先找这个。
- 面试话术:"我会警惕循环内查询——遍历用户逐条查订单就是 N+1,101 次查询变成 1 次 JOIN/IN,性能提升几十倍。"

### 23. 了解 SQL 注入 & 防注入 ■
- 不要字符串拼接 SQL；用参数化查询（`cursor.execute("... %s", params)`）或 ORM。

**SQL 注入是什么**：把用户输入直接拼进 SQL 字符串，输入里的引号/关键字被当成代码执行。**输入本是数据，被当成了代码** → 绕过认证、拖库、删库。

**经典攻击三连（面试讲案例很加分）**：
1. **登录绕过**：用户名输入 `' OR '1'='1' --` → `WHERE name='' OR '1'='1' --' AND pwd='...'`，`--` 注释掉后面，恒真 → 免密登录（常登录到管理员）。
2. **UNION 拖库**：`5 UNION SELECT name, pwd FROM users` → 商品查询结果里拼出所有用户名密码。
3. **堆叠删库**：`5; DROP TABLE users; --` → 分号追加第二条语句，把整张表连结构删掉。

**DROP 补课**：DDL（结构层）不是 DML（数据层）。DELETE 删行（表还在）、TRUNCATE 清空行（表还在）、**DROP 连表结构一起删，不可恢复**。最小权限账号（不给 DROP）就是防这条。

**参数化为什么让注入失效（核心机制）**：
- 拼字符串 = 发一整段"活" SQL，数据库从零解析，输入参与"造句"，能篡改句子结构。
- 参数化 = 发两样东西：**SQL 模板**（`%s` 占位符）+ **参数**（纯数据）。数据库**先编译模板**（此时注入内容根本没到，没机会参与语法解析），**再绑定参数**（只作为字符串值填入槽位，不再解析）。
- 结果：`' OR '1'='1` 只是"一个奇怪的名字"，查询找这个名字的用户 → 不存在 → 返回空。**输入永远是数据，永远当不了代码**。
- 类比：拼串=用户口述整句话；参数化=固定格式申请表，只能往"姓名"格里填内容。

**纵深防御四层**：①参数化查询（第一道）②输入校验（长度/类型/白名单）③数据库账号最小权限（不给 DROP）④密码哈希存储（bcrypt，不存明文，拖库也不值钱）。

**SQLAlchemy 写法**：ORM 底层就是参数化 → 不拼裸 SQL 自动防注入；裸 SQL 用 `text("... WHERE name = :n", {"n": username})` 命名占位符。

**面试一句话（背）**："SQL 注入是用户输入被拼进 SQL 当成代码执行，能绕过登录、UNION 拖库、DROP 删表。防注入核心是参数化查询：先编译 SQL 模板、输入作为纯数据绑定，永远成不了代码。再配合输入校验、最小权限、密码哈希做纵深防御。"

### 24. 缓存：Redis 基础
- Redis 是内存 KV，常用于缓存/限流/队列。
- 常见题：**缓存穿透**（查不存在 → 攻击流量直达 DB → 布隆过滤器或空值缓存）；**缓存击穿**（热点 key 失效 → 多重锁）；**缓存雪崩**（同一批 key 同时过期 → 随机过期时间）。

**Redis = 住在内存里的键值数据库**：读微秒级(硬盘毫秒级),断电丢数据、容量有限 → 只存"丢了不可惜"的热点数据。

**五种数据结构(背场景)**：
| 结构 | 是什么 | 场景 |
|---|---|---|
| String | key→值 | 缓存、计数(INCR)、限流 |
| Hash | key→字段:值(小 dict) | 存对象(用户信息) |
| List | 有序队列 | 简单 MQ、最新消息 |
| Set | 无序去重 | 去重、共同好友(交集) |
| ZSet | 带分数的 Set | **排行榜**(分数自动排序) |

**常用命令**：`SET/GET`、`INCR`(计数)、`HSET/HGET`、`LPUSH/RPOP`(队列)、`SADD/SISMEMBER`、`ZADD/ZREVRANGE`(排行榜)、`EXPIRE key 3600`(过期,缓存核心)。

**持久化(面试一句话)**：RDB 快照(定期拍快照存盘,快但可能丢最后一次)vs AOF 日志(记每个写操作,重启重放,慢但丢得少)。"Redis 是内存 KV 库,快但断电丢,所以有 RDB/AOF 持久化,按对丢数据的容忍度选。"

### 25. 部署与工程：Docker

**Docker 解决什么**："在我电脑上能跑啊!" → 环境差异(版本/依赖/系统)导致部署翻车。Docker 把"代码+依赖+环境"打包成镜像,任何机器跑起来一致。类比:密封套餐,到哪加热都一个味。

**三个概念**：镜像 Image(打包好的模板,只读)/ 容器 Container(镜像跑起来的实例)/ Dockerfile(描述怎么打包的配方)。

**Dockerfile 四行(面试背)**：

### 28. 数据库池 & 线程安全 ★
- 连接池（`pool_size` / `max_overflow`）：重用连接避免每次新建。
- 多线程读写共享对象：加锁 `threading.Lock`；或避免共享（每线程独立）；追求简单就选 `queue` / 协程。

**连接池为什么需要**：建一条数据库连接 = 网络握手 + 认证 + 分配内存，非常贵（几 ms ~ 几十 ms）。连接池 = 程序启动预开一批连接放池里，查询时"借一条、用完还"，开连接的昂贵成本只付一次。类比：共享单车 vs 每次买车。

**关键参数（SQLAlchemy）**：
```python
engine = create_engine("postgresql://user:pass@localhost/db",
    pool_size=10,        # 池里常备 10 条
    max_overflow=5,      # 紧急时最多再临时开 5 条
    pool_recycle=1800,   # 空闲超 30 分钟换新连接,防服务端掐断
)
```
- 池子借光：新请求排队等待，或超过 max_overflow 直接报错（保护数据库不被打垮）。
- 报错识别：`TimeoutError: QueuePool limit of size 10 overflow 5 reached` = 池子满了借不到。排查：①连接泄漏(借了不还) ②并发真大→调 pool_size ③慢查询占着连接→优化 SQL。

**线程安全铁律**：**一条连接不能多线程共用**（数据会串线！）。每个线程必须从池里借独立连接，用完归还。餐厅不共用一双筷子，各拿一套、用完放回消毒柜。
- **借了必须还**：用 with / try-finally 包裹，防止异常早退泄漏连接（和上下文管理器同一原理）。

**面试一句话（背）**："连接池预开一批连接复用，省去反复开-关的昂贵成本；池有上限、满了排队；pool_recycle 防空闲连接被服务端掐断。连接不是线程安全的，必须每线程借独立连接、用完归还，否则会连接泄漏或数据串线。"

# 十一、数据库扫盲与真题（SQL Server + MySQL）★核心章

> 这是 HR 和面试官双重点名的大项,也是你目前最薄弱、最需要**系统性扫盲**的领域。目标:三天后能面对任何"给场景写 SQL / 设计表 / 聊优化"的题不慌。

## 1. 关系型数据库核心概念

- **表 = 实体**,行 = 一条记录,列 = 一个字段。
- **主键 PK**：唯一标识一行,不能为空。**外键 FK**：引用另一张表的主键,保证数据一致性。
- **索引**：相当于书的目录,加速查询,代价是写入变慢、占空间。
- **范式**：
  - 1NF:每列不可再分(原子性);
  - 2NF:在1NF基础上,非主键列完全依赖主键(消除部分依赖);
  - 3NF:在2NF基础上,非主键列不依赖其他非主键列(消除传递依赖)。
  - 面试一句话:**设计表时先想清楚主键,再消除重复数据**。

## 2. SQL 四大类

| 类别 | 命令 | 干什么 |
|---|---|---|
| DQL | SELECT | 查询 |
| DML | INSERT / UPDATE / DELETE | 增改删 |
| DDL | CREATE / ALTER / DROP | 表结构 |
| DCL | GRANT / REVOKE | 权限 |

## 3. 基础查询必会写法

```sql
-- 查全部
SELECT * FROM users;
-- 条件 + 排序 + 限量
SELECT name, age FROM users WHERE age > 20 ORDER BY age DESC LIMIT 10;
-- 去重
SELECT DISTINCT city FROM users;
-- 模糊/范围/空值
SELECT * FROM users WHERE name LIKE '张%';        -- %任意, _单字符
SELECT * FROM orders WHERE amount BETWEEN 100 AND 500;
SELECT * FROM users WHERE phone IS NULL;          -- 空值必须 IS NULL,不能 = NULL
-- 多条件
SELECT * FROM users WHERE (city = '上海' OR city = '北京') AND age >= 18;
```

## 4. 聚合与分组（高频）

```sql
SELECT city, COUNT(*) AS cnt, AVG(age) AS avg_age, MAX(age), MIN(age), SUM(amount)
FROM users
GROUP BY city
HAVING COUNT(*) > 5       -- HAVING 筛分组,WHERE 筛行,顺序:WHERE → GROUP BY → HAVING
ORDER BY cnt DESC;
```

**必背差异**:`WHERE` 在分组**前**过滤行;`HAVING` 在分组**后**过滤组。

## 5. JOIN 全家（必考）

```sql
-- 内连接:两边都有的记录
SELECT u.name, o.id FROM users u INNER JOIN orders o ON u.id = o.user_id;
-- 左连接:左表全保留,右表无匹配为 NULL(最常用)
SELECT u.name, o.id FROM users u LEFT JOIN orders o ON u.id = o.user_id;
-- 右连接:反之
-- 全连接:两边都保留(MySQL 用 UNION 模拟)
```

**一句话**:LEFT JOIN 后 `WHERE 右表字段 IS NULL` = 查"左表里没有订单的用户"。

**JOIN 新手逐行拆解(面试讲得顺口版)**：
```sql
SELECT orders.goods, users.name          -- 列名带"表名."= 从哪张表拿,防两表同名列搞混
FROM orders                              -- 主表:一行一笔订单
JOIN users ON orders.user_id = users.id  -- 拼表规则:orders 的外键编号 = users 的主键 id
WHERE users.city = '上海';               -- 先拼表、再筛行(WHERE 在 JOIN 之后生效)
```
- 本质:**订单表只存 user_id 编号(不抄名字),需要名字时顺着外键去用户表取** → 这就是外键方向性:一边是权威源头(主键表),一边只是引用编号(外键表)。
- 类比:食堂打饭——饭票只写号(user_id),拿号去花名册对名字(users.id)。
- `AS total` 给列起别名,手写题加分。

**增删改 + 高危坑**：
```sql
INSERT INTO users (name, mobile, city) VALUES ('赵六', '136444', '深圳');
UPDATE users SET mobile = '138000' WHERE city = '上海';  -- 忘写 WHERE = 全表被改!
DELETE FROM users WHERE id = 5;                          -- 忘写 WHERE = 全表被删!
```
- **面试答"误删全表怎么发生的"**:UPDATE/DELETE 不带 WHERE 条件 → 全表遭殃。

**SQL 手写五步套路(拿到题按顺序问自己)**：
1. 几张表?→ 2 张以上 → JOIN + ON 关联条件
2. 要哪些列?→ SELECT(多表加表名前缀)
3. 要不要筛行?→ WHERE
4. 要不要分组/聚合?→ GROUP BY + COUNT/SUM/AVG
5. 分组后要不要筛组?→ HAVING

**聚合函数表**：COUNT(*) 数行数 / SUM 求和 / AVG 平均 / MAX / MIN。
- 铁律:SELECT 里的非聚合列必须出现在 GROUP BY 里,否则报错(一行代表一组,每列只能一个值)。

## 6. 子查询

```sql
-- 找出比平均年龄大的用户
SELECT * FROM users WHERE age > (SELECT AVG(age) FROM users);
-- IN 子查询
SELECT * FROM orders WHERE user_id IN (SELECT id FROM users WHERE city = '上海');
-- EXISTS(性能更好,只关心"是否存在")
SELECT * FROM users u WHERE EXISTS (SELECT 1 FROM orders o WHERE o.user_id = u.id);
```

## 7. 窗口函数（中级加分项,SQL Server/MySQL 8.0+ 支持）

```sql
-- 按城市分组,组内按年龄排名
SELECT name, city, age,
       ROW_NUMBER() OVER (PARTITION BY city ORDER BY age DESC) AS rn,   -- 1,2,3
       RANK() OVER (PARTITION BY city ORDER BY age DESC) AS rk,         -- 1,1,3(并列占位)
       DENSE_RANK() OVER (PARTITION BY city ORDER BY age DESC) AS dr    -- 1,1,2(并列不占位)
FROM users;
```

**经典场景**:取每组前 N 名 —— 用 ROW_NUMBER() 然后外层筛 rn 小于等于 N。**这个题型面试最爱考,背下模板**。

## 8. 索引（聊优化必考,重点背）

- **B+ 树索引**：数据有序存放,查找 O(log n)。
- **聚集索引**(InnoDB 主键):表数据物理顺序=索引顺序,一表一个。
- **非聚集索引**:独立结构,查到后再回表取数据(覆盖索引可避免回表)。
- **联合索引最左前缀**:`(a, b, c)` 上建索引,查询走 a、a+b、a+b+c 可用;只查 b 或 c **不走索引**。
- **索引失效场景(背 6 个)**:
  1. 对索引列做函数运算:`WHERE YEAR(create_time) = 2024`
  2. 隐式类型转换:字符串列 `= 123`
  3. LIKE 前导通配符:`LIKE '%abc'`
  4. 违反最左前缀
  5. OR 连接非索引列
  6. 大量数据且 `!=` / `NOT IN`(优化器可能放弃)
- **何时建索引**:WHERE/JOIN/ORDER BY 的列;区分度高的列;不要在小表、频繁更新的列上滥用。

## 9. 事务与 ACID（必考）

- **ACID**:原子性(全成或全败)、一致性(数据前后合法)、隔离性(事务互不干扰)、持久性(提交后不丢)。
- **隔离级别**(从松到严):
  1. 读未提交 —— 有脏读;
  2. 读已提交(SQL Server 默认、PG 默认)—— 解决脏读,有不可重复读;
  3. 可重复读(MySQL InnoDB 默认)—— 解决不可重复读,有幻读(靠间隙锁解决);
  4. 串行化 —— 全解决,性能最差。
- **三个问题背熟**:脏读(读到别人未提交)、不可重复读(同一条记录两次读不同)、幻读(同一范围两次查到行数不同)。

**ACID 原理层(怎么做到的?面试讲出这些词直接加分)**：
| ACID | 幕后工具 |
|---|---|
| 原子性 | **undo log**(操作前先记"旧值照片",失败照照片还原=回滚) |
| 持久性 | **redo log + WAL**(先写日志再改数据;提交=日志落盘,断电重启按日志重放) |
| 隔离性 | **锁 + MVCC**(锁管写写互斥;MVCC 多版本让读写并行) |
| 一致性 | 前三者合力的结果(不是独立机制) |

- **undo log 类比**:修车前拍零件原状照片,修坏了照照片装回去。
- **redo log / WAL 类比**:账房先生先在小本本上立刻记一笔(提交=落盘),打烊后才誊进大账本;小本本在,大账本烧了也能誊回。
- **锁**:写锁(排他)管"改",读锁(共享)管"读";公厕门锁——有人进去别人等。
- **MVCC 类比 = Git 分支**:读事务 checkout 一个快照,看"我事务开始那一刻"的版本;写事务提交新版本。读写并行互不干扰 → 这就是可重复读的实现原理。
- **一条 UPDATE 的完整流水线(终极面试题)**:写 undo log(留后路)→ 上行锁(隔离)→ 内存改数据 + 写 redo log → 提交(redo log 落盘=持久)→ 失败时照 undo log 还原。

## 10. 锁

- **行锁 / 表锁**:行锁粒度小并发高;表锁简单但阻塞多。
- **悲观锁**:查询时 `SELECT ... FOR UPDATE` 直接锁行,适合冲突多的场景。
- **乐观锁**:不加锁,更新时比对版本号 `SET version = version + 1 WHERE version = ?`,失败重试,适合冲突少的场景。
- **死锁**:两个事务互相持有对方要的资源。解决:按固定顺序访问、超时回滚、减少事务范围。

## 11. 慢查询优化（面试高频题"接口慢了怎么查"）

排查步骤:
1. 打开慢查询日志,找到慢 SQL;
2. `EXPLAIN` 看执行计划(关注 type 是否 ALL 全表扫、key 是否命中索引、rows 扫描行数);
3. 对症下药:加索引 / 改写 SQL(避免 SELECT *,拆分大查询)/ 分页优化;
4. 前端/应用层:加缓存、加 LIMIT。

**分页优化经典写法**(深分页):
```sql
-- 慢:OFFSET 越大越慢
SELECT * FROM orders ORDER BY id LIMIT 100000, 20;
-- 快:先只查主键
SELECT * FROM orders WHERE id > 100000 ORDER BY id LIMIT 20;
```

## 12. SQL Server 与 MySQL 差异(该团队 .NET 系,必看)

| 维度 | SQL Server | MySQL |
|---|---|---|
| 分页 | `OFFSET 10 ROWS FETCH NEXT 20 ROWS ONLY` / `TOP 20` | `LIMIT 10, 20` |
| 默认事务隔离 | READ COMMITTED | REPEATABLE READ |
| 存储过程 | T-SQL,支持大量逻辑 | 支持,不如 SQL Server 常用 |
| 触发器 | 有,常被用 | 有,慎用 |
| 当前时间 | `GETDATE()` | `NOW()` |
| 自增 | `IDENTITY(1,1)` | `AUTO_INCREMENT` |

**T-SQL 存储过程一句话**:把一段 SQL 逻辑预先编译存数据库,调用即执行;优点性能稳、复用;缺点难维护、版本难控。老系统(.NET)多,面试官可能会提。

## 13. 连接池与 ORM

- **连接池**:预先建好一批 DB 连接复用,避免每次请求都新建连接(建连接很贵)。FastAPI 里 SQLAlchemy `create_engine(pool_size=10, max_overflow=20)`。
- **ORM**(SQLAlchemy):用 Python 对象操作表,防 SQL 注入、代码友好;性能比原生 SQL 略低。
- **N+1 问题**(必考):查 1 条主记录 + 循环 N 次查子表 = N+1 次查询。解决:`joinedload` / `selectinload` 预加载,或一次 `IN` 查询。

## 14. SQL 真题 8 道(带答案,请自测后看答案)

**题1**：users(id, name, age, city)、orders(id, user_id, amount, create_time)。查出每个城市订单总金额,只显示总金额大于 10000 的城市,按金额降序。
> [!note]- 答案
>
> ```sql
> SELECT u.city, SUM(o.amount) AS total
> FROM users u JOIN orders o ON u.id = o.user_id
> GROUP BY u.city
> HAVING SUM(o.amount) > 10000
> ORDER BY total DESC;
> ```

**题2**：查出从未下过单的用户。
> [!note]- 答案
>
> ```sql
> SELECT u.* FROM users u
> LEFT JOIN orders o ON u.id = o.user_id
> WHERE o.id IS NULL;
> ```

**题3**：monitor(id, point_id, value, record_time) 监测表。查出每个监测点最近一条记录。
> [!note]- 答案
>
> ```sql
> SELECT point_id, value, record_time FROM (
>   SELECT *, ROW_NUMBER() OVER (PARTITION BY point_id ORDER BY record_time DESC) AS rn
>   FROM monitor
> ) t WHERE rn = 1;
> ```

**题4**：查出每个城市年龄最大的用户(含并列)。
> [!note]- 答案
>
> ```sql
> SELECT name, city, age FROM (
>   SELECT *, DENSE_RANK() OVER (PARTITION BY city ORDER BY age DESC) AS dr
>   FROM users
> ) t WHERE dr = 1;
> ```

**题5**：更新订单金额:把所有金额小于 100 的订单加 50 元。

> ```sql
> UPDATE orders SET amount = amount + 50 WHERE amount ＜ 100;
> ```

**题6**：删除重复数据,保留 id 最小的一条(用户表按 name+phone 判重)。
> [!note]- 答案
>
> ```sql

>   SELECT MIN(id) FROM users GROUP BY name, phone
> );
> ```

**题7**：某接口查询从 500ms 变成 5s,你会怎么排查?(口头题)

**题8**：设计一张订单表,要求支持:按用户查、按状态查、按时间范围查。(口头设计题)

# 十二、API 与应用开发扫盲（重点章）

## 1. HTTP 基础必背

- **方法**:GET(查,幂等)/ POST(增,非幂等)/ PUT(全量更新,幂等)/ PATCH(部分更新)/ DELETE(删,幂等)。
- **状态码**:
  - 2xx:200 OK / 201 创建成功 / 204 无内容
  - 3xx:301/302 重定向、304 未修改
  - 4xx:400 参数错 / 401 未认证 / 403 无权限 / 404 不存在 / 405 方法不允许 / 429 限流
  - 5xx:500 服务器内部错误 / 502 网关错 / 503 服务不可用 / 504 网关超时
- **幂等**:同一操作执行多次结果一致。GET/PUT/DELETE 幂等,POST 不幂等——面试常问"怎么保证重复提交不重复下单":唯一订单号 + 数据库唯一约束。

## 2. RESTful 设计规范

- URL 用**名词复数**,不用动词:`GET /users`、`POST /users`、`GET /users/1`。
- 查询用 query 参数:`GET /orders?status=paid&page=1&size=20`。
- 版本:`/api/v1/users`。
- 返回统一 JSON 结构:**{code: 0, msg: "ok", data: {...}}**——错误码与 HTTP 状态码分开,方便前端统一处理。

## 3. FastAPI 应用骨架(必会口述)

```python
from fastapi import FastAPI, Depends
from pydantic import BaseModel

app = FastAPI()

class UserIn(BaseModel):          # Pydantic 自动校验,非法自动 422
    name: str
    age: int = 0

@app.post("/users")
def create_user(user: UserIn, db: Session = Depends(get_db)):
    # 1. 校验(Pydantic 已完成) 2. 落库 3. 返回
    return {"code": 0, "data": {"id": 1, "name": user.name}}
```

**口述链路**:请求进来 → 路由匹配 → 依赖注入(db/鉴权)→ Pydantic 校验 → 业务逻辑 → 数据库读写 → 统一返回 JSON → 异常由全局处理器兜底。

## 4. FastAPI 高频考点

- **async 与同步**:FastAPI 自动在线程池跑同步函数;`async def` 用于 IO 密集(调外部 API、查库)。一句话:IO 密集用 async 提升并发,CPU 密集用进程。
- **依赖注入 Depends**:共享 db 连接、当前用户、配置。
- **中间件**:日志、CORS、限流、请求计时——每个请求前后执行。
- **全局异常处理**:
```python
@app.exception_handler(HTTPException)
async def handler(request, exc):
    return JSONResponse(status_code=exc.status_code, content={"code": exc.status_code, "msg": str(exc.detail)})
```
- **鉴权 JWT**:登录签发 token(header.payload.signature,payload 含用户 id/过期时间),后续请求带 `Authorization: Bearer ＜token>`,服务端验签即可,无需查库。

**全局异常处理——逐行执行轨迹(为什么会自动被调?)**：
```python
raise HTTPException(status_code=404, detail="用户不存在")
# ① raise 创建异常对象并抛出去(exc.status_code=404, exc.detail="用户不存在")
# ② FastAPI 看到异常飞出来,查"登记表" → 找到 @app.exception_handler(HTTPException) 登记的函数
# ③ 框架自动调用该函数,并自动塞参数:request=当前请求, exc=刚才那个异常对象
# ④ 函数里 exc.status_code→404, str(exc.detail)→"用户不存在",组装 JSONResponse 返回
```
- **核心心法**:`@app.exception_handler(...)` 只是"登记"(告诉框架这类异常来了叫谁),不是执行。你写"raise 包裹",框架负责"接住并调函数",函数负责"拆包裹组 JSON"。request/exc 你没传过——框架自动塞,和 self 自动传是同一个套路。
- **兜底版**:`@app.exception_handler(Exception)` 登记"所有异常的祖宗"→ 任何没专门登记的异常都归它,返回统一 500 JSON(业务代码只管抛,框架保证有人接、格式统一)。
- 业务代码不写 try/except,只管 raise;好处=返回格式统一+500 不泄漏内部堆栈+日志集中。

**JWT 鉴权——三层自动调用链(逐层拆)**：
```python
security = HTTPBearer()   # ① 第0层:框架自带"读卡器",从请求头 Authorization: Bearer <token> 掏出 token
                          #    creds.credentials = 那串 token 字符串

def get_current_user(creds: HTTPAuthorizationCredentials = Depends(security)):
    token = creds.credentials                 # ② 拿 token 串
    payload = decode_and_verify(token)        # ③ 验签+拆开 → {"user_id": 1, "exp": ...}
    return payload["user_id"]                 # ④ 交出用户 id(一个数字)

@app.get("/profile")
def profile(user_id: int = Depends(get_current_user)):
    return {"msg": f"你好,用户 {user_id}"}    # ⑤ user_id 是框架自动调 get_current_user 塞进来的
```
- **执行轨迹(多米诺骨牌)**:请求带 token 来 → profile 的 `Depends(get_current_user)` 触发 → 框架先调 get_current_user → 它内部又 `Depends(security)` → 框架再调 security 读卡器 → 取到 token → 验签拆开 → return user_id → 框架把 user_id 塞进 profile 参数 → 接口执行。
- **你只是声明"我依赖谁",跑腿的是框架**——所有魔法都是"你声明规则,框架自动调用自动塞参"。
- **联动**:验签失败抛异常 → 被上面的全局异常处理器接住 → 返回 401。鉴权=抛异常,处理=接住,两段代码接上了。
- 面试:JWT vs Session(JWT 无状态验签不查库,适合分布式);token 被盗→等过期(exp)或黑名单;401=没带/过期(你是谁),403=带了但没权限(你不行)。

## 5. API 工程化要点(面试聊"你做过什么接口"时用)

- **参数校验**:Pydantic(必填、类型、范围)。
- **分页**:page/size 参数 + LIMIT,深分页用游标。
- **限流**:Redis INCR 计数,如 1 分钟 60 次,超了返 429。
- **超时**:所有外部调用(LLM/第三方)设置 timeout,防止拖垮主接口。
- **重试**:网络抖动/限流 → 指数退避重试 2-3 次,注意幂等。
- **日志**:请求 id 贯穿全链路,记录入参出参、耗时、错误堆栈;分层 error/warning/info。
- **上传下载**:Excel/CSV 上传 → 校验格式 → 清洗 → 入库;下载用流式返回。

**分页 offset/limit 执行原理**:
- `OFFSET 40 LIMIT 20` = 跳过前 40 行,取接下来的 20 行(第 3 页)。
- **offset 越大越慢**:数据库要从第 1 行一路"路过"到目标位置,前面不返回的行也要数一遍(翻书找 5000 页,不能跳页)。
- **游标分页** `WHERE id > 上页末尾 ORDER BY id LIMIT 20`:利用主键索引直接定位,页数深也快。
- 面试答案:数据量小用 page/size;大表深分页用游标(id 记得上次位置,索引直达)。

**重试幂等三件套(防止重复下单)**:
1. 前端按钮防抖(第一层,防手滑连点);
2. 请求带唯一 request_id → 服务端 Redis 记录 `done:{req_id}` 标记,处理过就直接返回已创建结果(第二层,核心);
3. 数据库唯一索引兜底(第三层,最后防线)——两条相同 request_id 物理上不可能同时插入。
- 类比:电影票验票划掉标记,重复来不让再买。
- 面试答案:"幂等 = 唯一标识 + 去重,前端防抖、Redis 去重标记、数据库唯一索引三层防线,唯一约束是最后防线。"

**请求 ID 贯穿全链路(contextvars)**:
```python
import contextvars, uuid
request_id_var = contextvars.ContextVar("request_id", default="-")

@app.middleware("http")
async def add_request_id(request, call_next):
    request_id = uuid.uuid4().hex[:8]
    request_id_var.set(request_id)                 # 存入上下文
    response = await call_next(request)
    response.headers["X-Request-ID"] = request_id  # 响应头带上前端可见
    return response
# 业务代码深处:logger.info(f"[{request_id_var.get()}] 调 LLM 开始")  # 自动带当前请求 id
```
- **contextvars = 每个请求独立的一份变量**:请求 A 读到的永远是自己的 id,并发不串线(类比:进门发号牌,服务员报号不混淆)。
- 排查流程:前端报错 → 看响应头 X-Request-ID → 后端日志搜这个 id → 整个链路轨迹全捞出来。
- 面试答案:"中间件生成请求 id 存进 contextvars,全链路日志带上,响应头返回;出问题用 id 一搜全串起来。"

**接口会考虑(面试完整串联)**:"参数 Pydantic 校验,列表分页,敏感接口 Redis 限流(超了 429),外部调用设超时+重试(指数退避+幂等),全链路日志带请求 ID,统一返回 {code,msg,data},上传走 MQ 异步解析,下载流式返回。"

## 6. 消息队列概念(中级)

- **MQ(RabbitMQ/Kafka)是什么**:生产者发消息进队列,消费者异步处理,解耦 + 削峰。
- **典型场景**:上传大文件后台异步解析、发通知、日志采集、订单状态流转。
- **必懂词**:生产/消费、队列、exchange(交换机路由)、ack(确认消费,失败重投)、死信队列(处理失败的消息)。
- **为什么用**:请求不用等慢操作(报表生成/Excel 解析),用户感知快,高峰期消息排队慢慢消费。

**队列 = 先进先出(FIFO)的箱子**：任务排队,先来的先处理(奶茶店排队/栈是先进后出,队列是先进先出)。

**三个角色**：
| 角色 | 干什么 | 类比 |
|---|---|---|
| 生产者 Producer | 把任务放进队列 | 点餐的客人 |
| 队列 Queue | 存任务的地方(在 MQ 服务器上) | 餐厅订单架 |
| 消费者 Consumer | 从队列取任务处理(独立程序,循环拿任务) | 后厨厨师 |

**解耦 + 削峰(为什么用)**：
- 解耦：上传接口只丢消息立刻返回"成功",解析等慢活在消费者后台慢慢做——用户不等、主流程不卡;
- 削峰：1000 人同时上传,请求全部快速接受进队列排队,后台慢慢消费,系统不崩。
- 生产者和消费者互不认识,只通过队列传递消息。

**ack 机制(消息为什么不丢)**：消费者拿任务 → 队列标记"待确认" → 处理完必须 ack("我处理完了")→ 没 ack 就崩了 → 队列把消息重投给别人处理。类比:快递签收——没签收就重新分配。**保证消息不丢**。

**死信队列 DLQ(失败消息去哪)**：重试几次(如 3 次)还失败 → 丢进死信队列单独存放 → 人工排查。好处:坏任务不阻塞后面正常任务、失败消息不丢。类比:疑难杂症转专家会诊,不占急诊室。

**幂等消费(同一任务可能被处理两次!)**：消息可能重投 → 消费者重复执行会出 bug(如重复加积分)。方案:①业务唯一键去重(处理前查"done:订单id"标记,处理过就跳过)②数据库唯一索引兜底(重复插入被拒绝)。类比:报销单盖"已报销"章,重复送来看到章就跳过。

**exchange 交换机(RabbitMQ)**：生产者不直接丢队列,丢给交换机贴标签(routing key),交换机按规则路由到不同队列(错误日志→error 队列,普通日志→info 队列)。类比:快递分拣中心按地址分到不同车队。

**面试口述完整版**："上传 Excel,接口存好文件后往队列丢消息立刻返回'成功';消费者后台取消息解析入库生成报表,处理完 ack。消费者崩了没 ack 消息会重投,所以消费逻辑做幂等(业务唯一键去重);重试几次失败的消息进死信队列人工排查。好处:接口快、任务不丢、坏任务不阻塞好任务。"

## 7. API 设计真题 4 道

**题1**：设计一个"用户上传 Excel,系统解析入库并生成统计报表"的接口方案。
> [!note]- 推理过程
> ① 上传本身:收文件 → 校验格式/大小 → 存起来 → 返回任务 id;② 解析是慢操作 → 不能同步 → 丢 MQ 异步(解耦+削峰);③ 消费者:解析 → 清洗(去重/补缺/类型检查)→ 批量入库 → 生成报表;④ 用户怎么知道完成?→ 轮询任务状态或回调。核心:上传与处理解耦、失败重试、死信队列收容坏文件。
> [!note]- 答案
> POST /api/v1/files/upload(先存 Blob/本地)→ 异步任务解析(消息队列)→ 校验清洗(去重/补缺/类型检查)→ 批量入库 → 生成报表。前端轮询或回调拿结果。要点:上传与处理解耦、失败重试、文件大小限制。

**题2**：写一个注册接口,要求:校验用户名唯一、密码不能明文存。
> [!note]- 推理过程
> ① 接口入参 username/password → Pydantic 校验(长度/强度);② 用户名唯一怎么保证?先查一遍 + **唯一索引兜底**(并发同名时数据库拒绝一个);③ 密码不能明文 → **bcrypt 哈希**(不可逆,拖库也不怕);④ 返回:201 或直接签发 token,不返回密码、统一错误码。呼应:唯一索引=幂等最后防线,哈希=SQL 注入那学的纵深防御。
> [!note]- 答案
> POST /api/v1/register,入参 username/password(Pydantic 校验长度)。流程:查 username 是否存在(唯一索引兜底)→ 密码 bcrypt 哈希 → 入库 → 返回 token 或 201。注意:不返回密码、统一错误码。

**题3**：接口响应慢,前端一直转圈,你怎么排查?(全链路口头题)
> [!note]- 推理过程
> 按"线上排查四步"走:① 日志(请求 id 串链路)看耗时和错误堆栈;② 数据库慢查询(EXPLAIN 看走没走索引);③ 外部依赖(调了第三方没设超时?);④ 资源(CPU/内存/连接数)。递进顺序:日志 → 数据库 → 外部依赖 → 资源。
> [!note]- 答案
> 1. 看后端日志(耗时、错误);2. 查 DB 慢查询;3. 看是否调了外部接口没超时;4. 看中间件/限流是否卡住;5. 查服务器 CPU/内存。从"日志 → 数据库 → 外部依赖 → 资源"递进。

**题4**：如何保证"重复点击提交"不会创建两条重复订单?
> [!note]- 推理过程
> 用户连点两次 → 请求发两次 → 两次都创建订单 = 重复下单。三层防线:① 前端按钮防抖(第一层);② 请求带唯一 request_id,Redis 记"已处理"标记,处理过直接返回原结果(第二层,核心);③ 数据库唯一索引兜底(第三层,最后防线,两条相同 request_id 物理上不可能同时存在)。核心:唯一标识 + 去重。
> [!note]- 答案
> 1. 前端按钮防抖禁用;2. 后端幂等:请求带唯一 request_id(或业务唯一键,如订单号),服务端查重/唯一索引兜底;3. 事务保证。核心:**唯一约束是最后防线**。

## 1. 一次请求的全链路(必背)

## 2. 线上问题排查方法论(万能四步)

**日志 → 定位 → 修复 → 验证**:
1. 看日志(请求 id 串链路,错误堆栈);
2. 定位:慢查询?外部调用?资源(CPU/内存/连接数)?
3. 修复:索引/SQL/超时/重试/扩容;
4. 验证:压测/回归,观察监控告警。

**口头答题模板**:"我会先看日志确认错误类型,再用监控看接口耗时和依赖,慢就查 SQL,错就查堆栈,改完观察一段时间确认恢复。"

## 3. 缓存三兄弟(必背,第十章已列,这里给模板)

- **穿透**:查不存在的 key 一直打到 DB → 布隆过滤器或缓存空值。
- **击穿**:热点 key 过期瞬间大并发打到 DB → 互斥锁重建缓存。
- **雪崩**:大量 key 同时过期 → 过期时间加随机值 + 多级缓存。
- 口头:"缓存解决读多写少,但要注意穿透击穿雪崩,方案分别是空值缓存/互斥锁/随机过期。"

**三兄弟代码版(面试手写题对照)**：
- 穿透 → 查不到也写缓存(空值 + 短过期 300s):
```python
if data is None:
    r.set(f"product:{pid}", json.dumps(None), ex=300)   # 空值也缓存,防反复打库
    return None
```
- 击穿 → 互斥锁(只有 1 个请求查库重建,其他等待后读缓存):
```python
got = r.set(f"lock:{pid}", "1", nx=True, ex=10)   # nx=True=不存在才成功(抢锁),10s 自动过期防死锁
if got:
    try:
        data = db.query(...); r.set(f"product:{pid}", json.dumps(data), ex=3600)
    finally:
        r.delete(f"lock:{pid}")                    # 用完释放锁
else:
    time.sleep(0.05); cached = r.get(f"product:{pid}")   # 等别人重建好,读缓存
```
- 雪崩 → 过期时间加随机值错开:`ex=3600 + random.randint(0, 300)`;或热点数据不设过期+后台定时刷新。

**缓存一致性(Cache Aside,面试必考"数据变了缓存怎么更新")**：
- **问题**:只写不更 → 用户命中缓存看到过期数据(改库后缓存还是旧值)。
- **标准解法**:先更新数据库 → **删除缓存**(不是更新!)→ 下次查询没命中 → 查库拿最新 → 写回。
```python
def update_product(pid, price):
    db.update(pid, price=price)          # ① 先改库(数据库是唯一权威)
    r.delete(f"product:{pid}")           # ② 删缓存,下次查询自然回填新值

def get_product(pid):
    cached = r.get(f"product:{pid}")
    if cached is not None: return json.loads(cached)   # 命中返回
    data = db.query(...)                               # 没命中查库(最新)
    r.set(f"product:{pid}", json.dumps(data), ex=3600) # 写回
    return data
```
- **为什么删不更新**:并发下更新缓存顺序会乱(库改 A、缓存写 B → 不一致);删掉后缓存永远从库重新生成,不存在旧值覆盖。
- **顺序铁律**:必须先库后删(先删后改库,中间窗口有人读旧值写回缓存,旧数据就回来了)。
- **兜底双保险**:热点数据可长过期(24h)+ 删除保证一致,防止删缓存失败(Redis 挂/漏删)导致永远旧数据。
- **进阶**:延迟双删(删 → 睡 500ms → 再删,清掉窗口期写回的旧值);大厂用 Canal/CDC 订阅数据库变更日志异步删缓存(了解即可)。
- **面试答案**:"缓存一致性用 Cache Aside:先更新数据库,再删除缓存,下次查询自动回填新数据;顺序必须先库后删;删缓存而非更新缓存,避免并发更新顺序错乱;长过期兜底防漏删。"

## 4. 分布式高频词(每词一句人话)

| 词 | 一句话 |
|---|---|---|
| 幂等 | 同一请求重复执行,结果一样(靠唯一键兜底) |
| 限流 | 控制单位时间请求量(令牌桶/Redis 计数,超限返 429) |
| 降级 | 依赖挂了给兜底返回,不影响主流程 |
| 熔断 | 连续失败就短路不再调,等恢复再放行 |
| 超时 | 所有外部调用设上限,防止拖垮自己 |
| 重试 | 临时失败再试几次,指数退避 |
| 死锁 | 互相等对方锁,超时回滚解决 |
| 消息队列 | 削峰、解耦、异步 |

**降级展开**:依赖挂了 → 给"不那么好但能用"的兜底结果(推荐挂了返回热门榜单、AI 挂了返回预设回复),总比报错强。类比:停电切备用发电机。**降级是主动选择的兜底方案**。

**熔断展开**:监控失败率,连续失败超阈值(如 5 次)→ **短路**,直接拒绝调用不等待 → 过段时间放一个试探请求,成功则恢复、失败继续熔断。类比:电路保险丝,防止一个坏服务拖垮整个系统(雪崩)。
- **降级 vs 熔断区别**:降级=主动兜底(挂了返回备选);熔断=自动保护(检测持续失败,自动停止调用防拖垮自己)。关系:熔断触发后配合降级——熔断"不调了",降级"给兜底"。

**死锁展开**:事务 A 锁了 X 想锁 Y,事务 B 锁了 Y 想锁 X → 互相等对方 → 永远卡死。解决三招:①按固定顺序访问资源(都先锁 X 再锁 Y)②锁等待超时自动回滚 ③缩小事务范围、尽快提交释放锁。类比:十字路口互相挡路,红绿灯规定谁先走/等太久倒车让路。

**面试综合话术**:"调外部服务设超时,连续失败触发熔断不再调,同时降级兜底返回;内部操作注意幂等,数据库操作防死锁(固定顺序+超时回滚),高峰期配合限流和 MQ 削峰。"

# 十四、Python 中级补充题 12 道(第十章基础上加深)

> 第十章是基础 36 题,这里补中级——二面大概率从基础往中级延伸,背熟这些拉开差距。

1. **装饰器带参数怎么写?**
> [!note]- 答案
>
> ```python
> def repeat(n):
>     def decorator(func):
>         @functools.wraps(func)
>         def wrapper(*args, **kwargs):
>             for _ in range(n):
>                 func(*args, **kwargs)
>         return wrapper
>     return decorator
> ```
> 三层嵌套:最外层收参数,中层收函数,内层包装执行。
> [!note]- 展开(为什么三层?)
> `@repeat(3)` 的执行顺序:① 先执行 `repeat(3)` → 返回 decorator(n=3 被记住)② `decorator(hello)` → 返回 wrapper ③ `hello = wrapper` → 以后调 hello 实际调 wrapper,内部 for 执行 3 次 func。**每多一个配置就多包一层**。记忆:"一层收参数、二层收函数、三层收执行"。

2. **@property 是干什么的?**
> [!note]- 答案
> 把方法当属性访问:`obj.age` 而不是 `obj.age()`;可加 setter 做校验,替代 getter/setter 模板。常配合只读属性。
> [!note]- 展开(@property / setter 机制)
> `@property` 把方法变成一个"属性对象"(带机关的门),它自带三个子装饰器:`getter`(读)/ `setter`(写)/ `deleter`(删)。
> - 只注册 @property(没写 setter)→ 属性**只读**,赋值直接报错 AttributeError;
> - 写 `@name.setter` = 给属性对象登记"写操作处理函数":`u.name = "张"` 时 Python 自动调用它,先进校验(长度 < 2 → 抛 ValueError)再存 `self._name`;
> - 常用:只读计算属性(age 从 birth_year 现算)、写前校验(名字长度)、隐藏内部字段(_ 开头是"私有约定",君子协定非真私有)。
> - 类比:name 属性 = 带智能锁的门,getter=出门感应,setter=进门安检(先查再放行)。

3. **`__str__` 与 `__repr__` 区别?**
> [!note]- 答案
> `__str__` 给用户看(print 时调用,友好);`__repr__` 给开发者看(调试/控制台,尽量能还原对象)。没定义 __str__ 时,会退化用 __repr__。
> [!note]- 展开
> - `__str__` = 餐厅菜单(给客人:招牌红烧肉 38 元);`__repr__` = 后厨配方卡(给厨师:猪肉 200g、酱油 15ml,最好能还原对象);
> - 控制台/Jupyter 里直接输入对象回车,显示的永远是 __repr__;print 用 __str__;
> - 面试话术:"__str__ 面向用户友好可读,__repr__ 面向开发者尽量可还原,没定义 __str__ 时退化用 __repr__。"

4. **什么是 GIL,怎么绕开?**(加深版)
> [!note]- 答案
> CPython 同一时刻只能有一个线程执行字节码。CPU 密集用 multiprocessing(每个进程独立 GIL);IO 密集用线程/协程(等待时不占 GIL)。如果代码能卸载到 C 扩展,也不受 GIL 限制。
> [!note]- 加深点
> C 扩展(numpy/pandas 底层)不受 GIL 限制——CPU 密集真并行常靠它们。

5. **`async` 与 `await` 怎么工作?**
> [!note]- 答案
> async def 定义协程;await 挂起等待 IO,期间事件循环去跑其他协程;asyncio.run() 启动。关键:await 只阻塞当前协程,不阻塞整个线程。IO 密集并发场景吞吐大增。

6. **深拷贝浅拷贝,对嵌套列表分别什么效果?**
> [!note]- 答案
> `copy.copy` 只复制最外层,内层 list 仍共享引用——改内层会互相影响;`copy.deepcopy` 递归复制所有层,完全独立。考点:浅拷贝的两个列表 id 不同,但内部元素 id 相同。

7. **`yield from` 和 `yield` 区别?**
> [!note]- 答案
> `yield from iterable` 相当于 `for x in iterable: yield x`,委托给子迭代器,把子生成器的产出直接透传出去。用于生成器组合。
> [!note]- 展开
> `yield from` = "透传"快捷方式:`def flat(): yield from gen_a()` 等价于 `for x in gen_a(): yield x`。用于生成器组合/扁平化嵌套生成器,一行替代 for+yield。

8. **`*args` / `**kwargs` 接收和传参分别怎么写?**
> [!note]- 答案
> 定义时:`def f(*args, **kwargs)` 分别收成元组/字典;调用时:`f(*list, **dict)` 解包传入;解包赋值:`a, *rest = items`。注意顺序:位置参数 → *args → 默认参数 → **kwargs。

9. **with 语句原理是什么?**
> [!note]- 答案
> 调用对象的 `__enter__` 进入、`__exit__` 退出(无论是否异常都执行)。自定义用 `@contextlib.contextmanager` + yield 分隔前后逻辑。典型:文件、锁、数据库事务、连接。

10. **列表推导式里能不能加条件?**
> [!note]- 答案
> 能:`[x for x in range(10) if x % 2 == 0]`(过滤);还能双循环:`[x+y for x in a for y in b]`。比 for 循环快且简洁。

11. **什么是 PEP8 / 代码规范,面试怎么说?**
> [!note]- 答案
> PEP8 是官方风格指南:4 空格缩进、行宽 79、命名 snake_case、导入放顶部、空格规范。面试答:用 ruff/black 自动格式化,遵循 PEP8,变量命名清晰,函数单一职责。

12. **如何安全地删除列表元素?**
> [!note]- 答案
> 不要在 for 循环里直接删除(索引会乱)。方案:倒序遍历;或用列表推导式重建 `[x for x in lst if 条件]`;或过滤后赋值。经典面试陷阱题。
> [!note]- 展开(为什么正着删会出错 + range 三个参数)
> - **为什么错**:for 靠下标推进,删掉元素后后面整体前移,下标继续走 → 跳过元素(删 2 后 3 前移到下标 1,但循环已到下标 2,3 被跳过)。
> - **`range(len(lst)-1, -1, -1)` 三个参数**:起始=最后下标(len-1)、结束=-1(不含,走到 0 为止)、步长=-1(每次减 1)→ 产出 len-1 ... 0,倒序遍历整个列表。想包含 0,结束值必须写 -1(结束值不含)。
> - **为什么倒着删不跳**:删后面的元素不影响前面下标,已检查过的不重查(从队伍末尾揪人,前面的人往前挪但已查过)。
> - 最推荐方案:**推导式重建** `lst = [x for x in lst if x % 2 != 0]`,一行替代循环删除。
